## 一、方案总览

这套东西解决的其实是一个问题：**HTTP 是无状态的，服务端怎么认出"这个请求还是刚才那个人"**。本项目用三个部件配合完成：

| 部件 | 存放位置 | 职责 | 一句话 |
| --- | --- | --- | --- |
| **Session**（会话数据） | 服务端 Redis `sess:<sid>` | 记住 `userId`、`csrfToken` 等状态 | 真相在服务端 |
| **Cookie**（`sid`） | 浏览器 httpOnly cookie | 只存一个**会话 id**，不存数据 | 客户端只拿"取件码" |
| **CSRF Token** | 服务端 session 内 + 客户端内存 | 证明"写操作是本站页面自己发起的" | 防止别人借用你的 cookie |

三者解决的是不同威胁，缺一不可：

- 只有 Cookie 没有 Session：把 `userId` 直接放前端，等于把身份判断权交给客户端，可被随意伪造。
- 只有 Session 没有 Cookie：服务端无从知道请求属于哪个会话。
- Session + Cookie 没有 CSRF Token：**Cookie 会被浏览器自动携带**，攻击者不需要读 cookie，只要诱导受害者的浏览器向你的站点发一个跨站表单 POST，就自动"带着身份"完成了一次用户不知情的写操作。

选型理由：

- **会话状态放服务端（Redis）而不是 JWT**：后台管理类系统最需要的是「立即踢下线 / 立即失效」的能力。JWT 是无状态自包含的，签发后无法收回，必须再配一份黑名单，反而多一份状态。既然反正要一份状态，不如直接用 Session。
- **Redis 而不是进程内存**：内存版（默认 `MemoryStore`）重启即丢、无法水平扩容、且官方明确声明"不用于生产"。Redis 让会话跨实例共享，重启后用户仍是登录态。
- **Cookie 用 httpOnly**：会话 id 是"钥匙"，一旦被 JS 读到，"XSS 就能直接偷走整个会话"。httpOnly 让 `document.cookie` 读不到它，把 XSS 的危害从"账号被完全接管"压到"当次页面内的操作被劫持"。
- **Cookie 用 signed（express-session 默认行为）**：`sid` 值形如 `s%3A<sid>.<HMAC>`，签名只用来**防篡改**（防止攻击者自己编一个 sid 去撞别人的会话），它**不是**保密手段，所以 httpOnly 依然必要。
- **CSRF Token 绑定在服务端 session 里，而不是"双提交 Cookie"**：双提交模式下 token 也是 cookie，攻击者若能往你的域写 cookie（子域 XSS、中间人）就能同时伪造两边，校验形同虚设。放在 session 里，客户端唯一能证明"自己看得见 token"的途径就是真读到了响应体——跨站攻击者读不到（同源策略）。
- **用 `timingSafeEqual` 比较 token**：普通 `===` 会在第一个不同字符处返回，攻击者可以通过大量请求统计响应时间逐字节猜出 token。恒定时间比较把这个侧信道堵死。

## 四、Redis Key 设计

| Key | 类型 | Value | TTL | 用途 |
| --- | --- | --- | --- | --- |
| `sess:<sid>` | string（JSON） | `{ "cookie": {...}, "csrfToken": "...", "userId": "..." }` | `SESSION_TTL`（默认 86400s） | 会话全量数据 |

设计要点：

- **键名由 `connect-redis` 的 `prefix: "sess:"` 决定**，值为 session 对象序列化后的 JSON。`<sid>` 是 express-session 生成的 24 字节随机串（base64url 后 32 字符，如 `dp6WVmfnxsFP_68ptJhPvNeRLdmWKihm`）。
- **Redis 里只有 key 存在 / 不存在的区别**。键不存在 = 会话无效（过期、被 `destroy`、或重启换过 `SESSION_SECRET`），中间件会当作"新访客"处理，不会报错。
- **空会话不落库**：`saveUninitialized: false` 意味着只要一次请求没有真正写入 `req.session`（例如 `GET /health`、无 cookie 的 `POST /api/danger`），就不会占用一个 Redis 键。这是"防止匿名请求把 Redis 撑爆"的关键开关，实测见第六节步骤 1 与步骤 10。
- **TTL 由 cookie 的 `maxAge` 推导**：`connect-redis` 会取 `cookie.maxAge` 作为 Redis 的 `EX`。实测 `TTL sess:<sid>` = `86400`，与 `SESSION_TTL` 一致。
- **`rolling: false`**：会话 TTL 不随每次请求续期。用户连续操作 24 小时以上仍会被要求重新登录。若要"滑动过期"，把它改成 `true`，代价是每次请求都要写一次 Redis（且要留意 `touch` 的写放大）。

## 五、核心实现

### 1. `.env` / `.env.example`

```env
NODE_ENV=development
PORT=3000

# Session node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
SESSION_SECRET=please-change-me-to-a-long-random-string
SESSION_NAME=sid              # cookie 名

# Redis
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_PASSWORD=123456
SESSION_TTL=86400             # 秒，session 过期时间
```

要点：

- **`SESSION_SECRET` 用随机值，不要手敲**：`node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` 生成 64 位十六进制串。它决定 sid 的 HMAC 签名密钥，泄露等于可以任意伪造会话 id。
- **`SESSION_TTL` 用秒**：因为它同时要换算成 cookie 的 `maxAge`（`* 1000`）和 Redis 的 TTL。
- **`REDIS_PASSWORD` 与根目录 `backend/.env` 保持一致**，Redis 容器由根目录 `docker-compose.yml` 启动，密码通过 `--requirepass ${REDIS_PASSWORD}` 注入。
- 本项目用的是 `import "dotenv/config"`，即**从进程的当前工作目录**加载 `.env`。所以必须在项目目录里启动（`cd "Session + Cookie + CSRF Token" && node index.ts`）；从别处启动会读不到 `.env` 而直接抛「环境变量未定义」。这与 `jsonwebtoken + Redis` 那个项目的多路径加载策略不同。
- `.gitignore` 里是 `.env`，`.env.example` 才是提交给别人的模板。

### 2. `config/env.ts` —— 强类型环境变量

> 因 `erasableSyntaxOnly` 禁用 `enum`，用 `as const` + 联合类型代替。

```ts
import "dotenv/config";

function getEnv(key: string, defaultValue?: string): string {
	const value = process.env[key];
	if (!value) {
		if (defaultValue !== undefined) {
			return defaultValue;
		}
		throw new Error(`环境变量 ${key} 未定义`);
	}
	return value;
}

export const env = {
	nodeEnv: getEnv("NODE_ENV", "development") as
		| "development"
		| "production"
		| "test",
	port: parseInt(getEnv("PORT", "3000"), 10),
	sessionSecret: getEnv("SESSION_SECRET"),
	sessionName: getEnv("SESSION_NAME"),
	redis: {
		host: getEnv("REDIS_HOST", "localhost"),
		port: parseInt(getEnv("REDIS_PORT"), 10),
		password: getEnv("REDIS_PASSWORD") || undefined,
	},
	sessionTtl: parseInt(getEnv("SESSION_TTL", "3600"), 10), // Session TTL in seconds
	isProd: getEnv("NODE_ENV") === "production",
} as const;
```

要点：

- **`sessionSecret` 和 `sessionName` 没有默认值**，缺失就抛错启动失败。这是故意的：这类安全参数绝不允许"悄悄用一个默认值跑起来"，宁可在启动时炸掉。
- **`password: getEnv("REDIS_PASSWORD") || undefined`**：空串转 `undefined`，否则 node-redis 会带着空密码去 `AUTH` 而连接失败。
- **`isProd` 决定三个开关**：cookie 的 `secure`、以及 cookie 在 `clearCookie` 时要保持一致的属性。注意它用的是 `getEnv("NODE_ENV")`（不带默认值），含义是"显式声明为 production 才算生产环境"，默认更保守。

### 3. `redis/client.ts` —— Redis 单例 client

```ts
import { createClient, type RedisClientType } from "redis";
import { env } from "../config/env.ts";

let client: RedisClientType | null = null;

export async function getRedisClient(): Promise<RedisClientType> {
	if (client) return client;
	client = createClient({
		socket: { host: env.redis.host, port: env.redis.port },
		password: env.redis.password,
	}) as RedisClientType;

	client.on("error", (err) => {
		console.error("[Redis] client error", err);
	});
	await client.connect();
	return client;
}
```

要点：

- **模块级 `let client` 做单例**：`connect-redis` 也建议复用同一个 client，避免每个请求新建连接。
- **必须注册 `error` 监听**，否则连接中断会变成 unhandled error 直接崩进程。
- **`await client.connect()` 在启动期完成**（见第 10 节 `createApp()`），不懒加载到第一个请求——否则第一个用户会替所有人承担连接延迟，且配置错误只能在运行时才暴露。
- 连接失败的实测表现：node-redis 会按内置策略持续重连，`connect()` 既不 resolve 也不 reject，于是 `createApp()` 永远不返回、端口不监听，日志里持续刷 `[Redis] client error ... EPERM/ECONNREFUSED`。**这是一种 fail-closed（宁可起不来也不降级）的行为**，但也意味着容器编排里必须给 Redis 配健康检查与启动顺序，否则表现为"进程活着但服务不可用"。

### 4. `types/session.d.ts` —— 给 `req.session` 加类型

```ts
import "express-session";

declare module "express-session" {
	interface SessionData {
		csrfToken?: string;
		userId?: string;
	}
}
```

要点：

- express-session 的 `SessionData` 是官方预留的扩展点，模块增强（module augmentation）后 `req.session.userId` 就有类型了，不需要到处 `as any`。
- **两个字段都声明为可选**：它们只在特定流程后才存在（`csrfToken` 取过 token 后才有、`userId` 登录后才有），声明成必填会与 `saveUninitialized: false` 的事实相矛盾。
- `import "express-session"` 是必须的，否则这个文件会被当成全局脚本而非模块，`declare module` 的语义会出错。

### 5. `utils/crypto.util.ts` —— 随机 token 与恒定时间比较

```ts
import { randomBytes, timingSafeEqual } from "node:crypto";

export function generateCsrfToken(): string {
	return randomBytes(32).toString("base64url");
}

export function safeEqual(a: string, b: string): boolean {
	const ab = Buffer.from(a);
	const bb = Buffer.from(b);
	if (ab.length !== bb.length) return false;
	return timingSafeEqual(ab, bb); //恒定时间比较，防时序攻击
}
```

要点：

- **`randomBytes(32)` = 256 bit 熵**，base64url 编码后是 43 个字符（实测样例：`rPqJKdF_swJ5AHfpWJZ-KbEFTeu0y9lj3gfpeRo5cnk`）。绝不能用 `Math.random()` 或时间戳拼接——它们可预测。
- **必须先比长度再 `timingSafeEqual`**：`timingSafeEqual` 在两个 buffer 长度不同时会直接 throw，而不是返回 `false`。长度不同即判不等是正确的（token 长度固定，长度不同一定是伪造的），且这一步不泄露有用信息。
- 比较对象是等长的 base64url 字符串，直接 `Buffer.from(str)` 用默认 utf8 编码即可，无需再做 base64 解码。
- 这是**纯函数模块**，不 import express、不碰 Redis，方便单测。

### 6. `middleware/session.ts` —— 会话中间件（核心）

```ts
import session from "express-session";
import { getRedisClient } from "../redis/client.ts";
import { RedisStore } from "connect-redis";
import { env } from "../config/env.ts";

export async function buildSessionMiddleware() {
	const redisClient = await getRedisClient();
	return session({
		store: new RedisStore({
			client: redisClient,
			prefix: "sess:",
		}),
		name: env.sessionName, // cookie 名，默认 connect.sid
		secret: env.sessionSecret,
		resave: false,
		saveUninitialized: false,
		rolling: false,
		cookie: {
			httpOnly: true,
			sameSite: "lax",
			secure: env.isProd,
			maxAge: env.sessionTtl * 1000,
		},
		// connect-redis 会自动用 cookie 的 maxAge 作为 TTL，也可显式 ttl
		// ttl: env.sessionTtl,
	});
}
```

这 6 个选项每个都在防一种坑，逐条说明：

| 选项 | 值 | 不这么设会怎样 |
| --- | --- | --- |
| `store` | `RedisStore` | 默认 `MemoryStore` 重启即掉线、多实例不共享，官方明说不用于生产 |
| `name` | `sid`（可配） | 默认 `connect.sid` 等于向攻击者宣告技术栈；改名属于最小化的信息隐藏 |
| `resave` | `false` | `true` 会让**每个请求**都回写 Redis，即使 session 没变，纯属浪费写 IO；并发请求还会互相覆盖 |
| `saveUninitialized` | `false` | `true` 会给每个匿名访客（含爬虫/健康检查）都建一个 Redis 键，等于给了一个廉价的存储耗尽攻击面 |
| `rolling` | `false` | 见第四节：`false` 是固定 TTL，`true` 是"每次请求续命"的滑动过期 |
| `cookie.maxAge` | `SESSION_TTL * 1000` | 不设就是**会话 cookie**（关浏览器即失效）；设了才是"持久 cookie"，并同时决定 Redis TTL |

要点：

- **`buildSessionMiddleware` 是 async 工厂**：因为要先 `await getRedisClient()` 拿到连接，再 `new RedisStore(...)`，最后返回中间件函数。`app.use(await buildSessionMiddleware())` 的写法见第 10 节。
- **cookie 的 `secure: env.isProd`**：开发环境走 http，若强设 `secure: true`，浏览器会直接丢弃这个 cookie，表现为"永远拿不到 session 且没有任何报错"，非常难排查。生产必须由 HTTPS + `trust proxy` 保证它真的生效（见第十二节）。
- **`sameSite: "lax"`**：跨站请求（POST 表单、跨域 XHR）不会带上这个 cookie，等于在浏览器层先挡掉一大类 CSRF；同时保留"从外链点进来时仍是登录态"的体验（`strict` 会在这个场景丢一次会话）。
- **`maxAge` 单位是毫秒**，`SESSION_TTL` 是秒，别忘了 `* 1000`。写错了会得到一个"1.5 小时后过期"之类的诡异现象。

### 7. `middleware/csrf.ts` —— 发放与校验 CSRF Token（核心）

```ts
import type { NextFunction, Request, Response } from "express";
import { generateCsrfToken, safeEqual } from "../utils/crypto.util.ts";

const UNSAFE_METHODS = new Set(["POST", "PUT", "PATCH", "DELETE"]);

export function issueCsrfToken(req: Request, res: Response) {
	if (!req.session.csrfToken) {
		req.session.csrfToken = generateCsrfToken();
	}
	res.json({ csrfToken: req.session.csrfToken });
}

export function csrfGuard(req: Request, res: Response, next: NextFunction) {
	if (!UNSAFE_METHODS.has(req.method)) {
		return next();
	}
	const sessionToken = req.session.csrfToken;
	const clientToken =
		(req.headers["x-csrf-token"] as string | undefined) ||
		(req.body && typeof req.body._csrf === "string"
			? req.body._csrf
			: undefined);

	if (!sessionToken || !clientToken) {
		return res.status(403).json({ error: "CSRF token missing" });
	}
	if (!safeEqual(clientToken, sessionToken)) {
		return res.status(403).json({ error: "CSRF token invalid" });
	}
	next();
}
```

要点：

- **发放逻辑是幂等的**：`if (!req.session.csrfToken)` 保证同一会话拿到的永远是同一个 token。实测连续两次 `GET /csrf/token` 返回完全相同的值——这一点很重要，否则多标签页会把彼此的 token 冲掉。
- **token 存进 `req.session` 就意味着"写会话"**，于是 `saveUninitialized: false` 下这次请求会真的在 Redis 建键并下发 `Set-Cookie`。这是本项目里唯一"匿名请求也会建会话"的入口，属于预期行为。
- **只拦"非安全方法"**：`GET / HEAD / OPTIONS` 直接放行（HTTP 语义上它们必须没有副作用）。`POST/PUT/PATCH/DELETE` 一律要 token。实测：`DELETE /health` 同样被 403 拦下（虽然该路由本身不存在）。
- **两种携带方式**：优先读 `X-CSRF-Token` 请求头，其次读 body 里的 `_csrf` 字段。前者给 SPA/`fetch` 用，后者给传统表单用。两者都实测可用。
- **两种失败原因刻意区分**：`CSRF token missing`（压根没带 / 服务端 session 里没有）与 `CSRF token invalid`（带了但值不对）。前者通常意味着"会话已销毁，需要重新取 token"，后者通常意味着"前端拿错了 token 或存在攻击"。客户端可据此分别处理。
- **`req.session.csrfToken` 缺失也返回 403 而不是 500**：`saveUninitialized: false` 下，一个没有 cookie 的陌生客户端访客必然走到这个分支，这是正常输入而不是异常，不该用 5xx。
- **校验发生在真正的业务处理之前**，所以被拦下的请求不会产生任何副作用（错误信息统一是 `403`，也避免了对攻击者泄露"该接口存在且参数正确"这类信息）。

### 8. `routes/csrf.routes.ts` —— 取 token 接口

```ts
import { Router } from "express";
import { issueCsrfToken } from "../middleware/csrf.ts";

export const csrfRouter = Router();
csrfRouter.get("/csrf/token", issueCsrfToken);
```

要点：

- **用 `GET` 是故意的**：这是页面加载时的"预取"动作，必须是无副作用的语义。它本身会创建会话，但由于 `csrfGuard` 只拦写操作，这个接口天然不被自己拦。
- 路由本身极薄，逻辑全在 `issueCsrfToken` 里，方便别处（比如登录成功后想强制换 token）复用同一个函数。
- **必须挂载在 `csrfGuard` 之前**（见第 10 节）。顺序反了的话，`GET` 虽然放行，但将来若有人把取 token 改成 `POST`，就会陷入"要 token 才能拿 token"的死锁。

### 9. `routes/auth.router.ts` —— login / logout

```ts
import { Router, type Request, type Response } from "express";
import { env } from "../config/env.ts";

export const authRoutes = Router();

authRoutes.post("/api/login", (req, res) => {
	req.session.userId = "u1";
	res.json({ ok: true });
});

authRoutes.post("/api/logout", (req: Request, res: Response) => {
	// 1. 没有会话：直接清 cookie 并返回
	if (!req.session) {
		res.clearCookie(env.sessionName, {
			httpOnly: true,
			sameSite: "lax",
			secure: env.isProd,
		});
		return res.json({ ok: "true", message: "logged out" });
	}
	req.session.destroy((err) => {
		// 2. 删 Redis 里的 session（connect-redis 自动 DEL sess:<sid>）
		if (err) {
			console.error("[logout] destroy error", err);
			return res.status(500).json({ error: "logout failed" });
		}
		// 3. 清浏览器 cookie —— options 必须与 session cookie 的 path/domain 一致
		res.clearCookie(env.sessionName, {
			httpOnly: true,
			sameSite: "lax",
			secure: env.isProd,
			// path: "/",        // 若 session cookie 显式设了 path，这里也要一致
			// domain: "example.com",
		});
		// 4. 告诉前端丢弃内存里的 csrfToken（下次登录重新取）
		return res.json({ ok: true, message: "logged out" });
	});
});
```

要点：

- **登录只是往 `req.session.userId` 写值**。真实项目这里应换成账号密码校验（查库 + bcrypt/argon2 比对 + 失败次数限制），代码结构不变。
- **`req.session.destroy()` 是"服务端失效 + 客户端清 cookie"两件事的合体**：`connect-redis` 会 `DEL sess:<sid>`，express-session 会紧接着下发清空 cookie。实测登出后 `sess:*` 键数从 1 变 0，且响应头出现 `Set-Cookie: sid=; Expires=Thu, 01 Jan 1970`。
- **`clearCookie` 的属性必须与签发时一致**：cookie 的唯一标识是 `(name, domain, path)`，其中任一不一致浏览器都不会执行删除。`httpOnly/sameSite/secure` 虽然不参与标识，但保持一致是良好习惯（部分实现/代理会据此判断）。本项目没显式设 `path`，两边都取默认 `/`，所以实测能正常清掉。
- **`destroy` 是回调式的**（express-session 至今保留 callback 风格），必须在回调里再回响应，否则可能在 Redis 删除完成前就把 200 返回给客户端，出现"前端以为已登出、实际旧会话还能用"的竞态。
- **`if (!req.session)` 是防御性代码，实际是死分支**：express-session 会给每个请求都装上 `req.session` 对象，因此这里永远进不去。保留它无害（万一将来中间件顺序变化或换成别的实现），但不要指望它承担逻辑。详见第十二节。
- **注意 `ok: "true"` 是字符串**（另一个分支是布尔 `true`）。统一成布尔更好，属于待清理的小瑕疵。

### 10. `app.ts` —— 组装（中间件顺序是关键）

```ts
import express, { type Express } from "express";
import helmet from "helmet";
import cors from "cors";
import cookieParser from "cookie-parser";
import { buildSessionMiddleware } from "./middleware/session.ts";
import { csrfRouter } from "./routes/csrf.routes.ts";
import { csrfGuard } from "./middleware/csrf.ts";
import { authRoutes } from "./routes/auth.router.ts";

export async function createApp(): Promise<Express> {
	const app = express();

	app.set("trust proxy", 1); // 生产在反向代理后；开发可设 0/false

	app.use(helmet());
	app.use(cors({ origin: true, credentials: true }));
	app.use(express.json());
	app.use(cookieParser());

	// session 必须在依赖 req.session 的中间件之前
	app.use(await buildSessionMiddleware());

	// 取 token：放 guard 之前
	app.use(csrfRouter);

	// 对写操作统一拦截
	app.use(csrfGuard);
	app.get("/health", (_req, res) => res.json({ ok: true }));

	app.use(authRoutes);

	app.post("/api/danger", (req, res) => {
		res.json({ ok: true, useId: req.session.userId });
	});
	return app;
}
```

**中间件顺序就是本项目的安全模型**，自上而下每一环都依赖上一环：

```text
trust proxy  →  secure cookie 判定依据（生产）
helmet       →  安全响应头
cors         →  跨域 + 允许携带 cookie
express.json →  解析 body，csrfGuard 才能读 req.body._csrf
cookieParser →  解析 cookie，express-session 需要（解析签名 cookie 时也用到它的 secret）
session      →  产生 req.session（Redis 存储在背后）
csrfRouter   →  提供 GET /csrf/token，放进 session
csrfGuard    →  拦截所有 POST/PUT/PATCH/DELETE 并要求 token
路由         →  业务逻辑，此时 session 与 CSRF 都已校验完毕
```

要点：

- **`express.json()` 必须在 `csrfGuard` 之前**：否则 body 形式的 `_csrf` 永远是 `undefined`，只有 header 方式能用。实测两种方式都通，正是因为这个顺序。
- **`cookieParser()` 必须在 `session` 之前**：express-session 依赖它读取 cookie（在解析 signed cookie 时还会用到同一个 `SESSION_SECRET`）。
- **`csrfRouter` 在 `csrfGuard` 之前**：保证"取 token"这个唯一不需要 token 的写操作前置入口不被自己拦住。
- **`csrfGuard` 用 `app.use(...)` 全局挂载而不是逐个路由加**：新增业务路由时默认就是安全的（默认拒绝），不会因为忘记加中间件而漏一个接口。代价是任何需要"免 CSRF"的接口（例如第三方 webhook）必须显式白名单化。
- **`cors({ origin: true, credentials: true })`**：`credentials: true` 才允许跨域携带 cookie，且此时浏览器不允许 `Access-Control-Allow-Origin: *`，所以 `origin: true`（回显请求来源）是开发期的省事写法，生产必须换白名单，见第十二节。
- **`trust proxy: 1`**：生产在 nginx/CDN 后面时，Express 才相信 `X-Forwarded-Proto`，`secure` cookie 的判断才成立。开发环境直连可以设 `0/false`。注意它是**跳数**，前面有几层代理就写几，写错会导致 secure 判断失效或可被伪造。
- **`/api/danger` 的 `useId` 是拼写笔误（应为 `userId`）**。实测响应：登录前 `{"ok":true}`（值为 `undefined`，被 `JSON.stringify` 丢弃），登录后 `{"ok":true,"useId":"u1"}`。

```ts
import { createApp } from "./app.ts";

async function main() {
```

## 六、完整流程与时序

### 请求链路一：拿 token（建立会话）

1. 前端加载页面后先 `GET /csrf/token`。
2. 请求没带 cookie → express-session 生成新 sid → `issueCsrfToken` 往 `req.session.csrfToken` 写入随机值 → 触发一次真正的 session 保存 → 响应 `Set-Cookie: sid=...; HttpOnly; SameSite=Lax; Expires=+86400s` + body `{"csrfToken":"..."}`。
3. 前端把 token 存内存（不要存 localStorage）。

### 请求链路二：写操作（校验 token）

1. 前端 `POST /api/danger`，带上 `Cookie: sid=...` 与 `X-CSRF-Token: ...`。
2. `csrfGuard` 从 header 取到客户端 token，从 `req.session` 取到服务端 token。
3. 任一缺失 → `403 CSRF token missing`；长度或内容不等 → `403 CSRF token invalid`；相等 → 放行到业务路由。

### 请求链路三：登录 / 登出

1. `POST /api/login`（同样要带 CSRF token）→ 服务端写 `req.session.userId` → 会话数据被回写 Redis。
2. `POST /api/logout` → `req.session.destroy()` → Redis 删键 + 浏览器 cookie 被清空 → 同一会话的旧 CSRF token 也随之消失（因为它就存在那个 session 里）。

```text
浏览器                                  Express                       Redis
  |  GET /csrf/token                     |                              |
  |  (无 cookie)                          |                              |
  |------------------------------------->|  req.session 不存在          |
  |                                      |  csrfToken = <random32B>     |
  |                                      |----------------------------->|  SET sess:<sid> {...} EX 86400
  |<--- Set-Cookie: sid=s%3A<sid>.<sig> -|                              |
  |<--- { csrfToken: "rPqJ..." } --------|                              |
  |                                      |                              |
  |  POST /api/danger  (无 token)         |                              |
  |------------------------------------->|  guard: clientToken 缺失      |
  |<--- 403 { error: CSRF token missing }-|  (无副作用、不写 Redis)       |
  |                                      |                              |
  |  POST /api/danger                    |                              |
  |  Cookie: sid=...                     |                              |
  |  X-CSRF-Token: rPqJ...               |                              |
  |------------------------------------->|  safeEqual(客户端, session)   |
  |<--- 200 { ok: true } -----------------|                              |
  |                                      |                              |
  |  POST /api/login                     |                              |
  |  Cookie: sid=...                     |                              |
  |  X-CSRF-Token: rPqJ...               |                              |
  |------------------------------------->|  session.userId = "u1"       |
  |                                      |----------------------------->|  SET sess:<sid> {... userId:"u1"}
  |<--- 200 { ok: true } -----------------|                              |
  |                                      |                              |
  |  POST /api/logout                    |                              |
  |  Cookie: sid=..., X-CSRF-Token: ...  |                              |
  |------------------------------------->|  session.destroy()           |
  |                                      |----------------------------->|  DEL sess:<sid>
  |<--- Set-Cookie: sid=; Expires=1970 --|                              |
  |<--- 200 { ok:true, message:... } -----|                              |
  |                                      |                              |
  |  POST /api/danger (复用旧 token)      |                              |
  |------------------------------------->|  新会话无 csrfToken           |
  |<--- 403 { error: CSRF token missing }-|                              |
```

## 七、Cookie 属性逐项说明

**实测**，`GET /csrf/token` 的响应头原文：

```http
Set-Cookie: sid=s%3A6sW5rMb8lFFUh6yj7FJXJPtvnVcVd5vV.9xp7E9pLmVtl2fSU7AfwSWo%2FUk4UpY%2FxCkkZWCIbzxg; Path=/; Expires=Sun, 20 Sep 2026 16:06:55 GMT; HttpOnly; SameSite=Lax
```

登出时：

```http
Set-Cookie: sid=; Path=/; Expires=Thu, 01 Jan 1970 00:00:00 GMT; HttpOnly; SameSite=Lax
```

| 属性 | 实测值 | 作用 |
| --- | --- | --- |
| 值 | `s%3A<sid>.<sig>` | `s:` 前缀表示"已签名"，`<sid>` 是 24 字节随机串的 base64url（32 字符），`<sig>` 是 HMAC-SHA256 签名。整体 URL 编码（`:` → `%3A`） |
| `Path` | `/`（默认） | 全站携带。若想收敛暴露面（如只给 `/api`）需在 session 配置里同步设 `path`，且 `clearCookie` 必须一致 |
| `Expires` | 当前时间 + 86400s | 来自 `cookie.maxAge = SESSION_TTL * 1000`。注意 express-session 发的是 `Expires` 而**不是** `Max-Age`，行为等价 |
| `HttpOnly` | 有 | `document.cookie` 读不到，防 XSS 直接窃取会话 |
| `SameSite` | `Lax` | 跨站 POST/PUT/…/XHR 不携带 → 浏览器层先挡一层 CSRF；顶级 GET 导航仍携带，保住外链跳转的登录态 |
| `Secure` | 开发环境**没有**，生产为 `true` | 只允许 HTTPS 传输，防中间人窃听。开发走 http 故必须关掉，否则浏览器直接丢弃 cookie |
| `Domain` | 未设置 | 未设置 = 仅当前主机（不含子域），这是更安全的默认值，不要随意设成 `.example.com` |

要点与坑：

- **签名只防篡改，不防读取**。`s%3A...` 里的 sid 是明文可见的（httpOnly 只是不让 JS 读，抓包/用户自己看 cookie 都能看到）。所以 sid 必须有足够熵且服务端不可预测——express-session 默认用 `uid-safe` 生成，符合要求。
- **篡改 cookie 不会报错，会被当成"没有会话"**。实测：带一个伪造的 `sid=s%3Abogus.bogus` 请求 `/csrf/token`，得到的是 200 + 一个**全新会话**的新 token，而不是 401。这个设计是对的（用户看到的是"重新登录"而非"系统报错"），但排查问题时要知道"cookie 坏了不报错"。
- **`Clear-Site-Data` 不参与**：本项目靠 `clearCookie` 清 cookie，够用；若前端还存了别的敏感数据，登出时可以额外发 `Clear-Site-Data: "cache", "cookies", "storage"`。
- **生产建议加 `__Host-` 前缀**（如 `__Host-sid`）：浏览器强制要求该 cookie 必须 `Secure` + `Path=/` + 无 `Domain`，能从根上杜绝子域写入 cookie 的攻击。改名后 `SESSION_NAME` 与 `clearCookie` 会自动跟着走。

## 八、CSRF 防护原理

### 攻击模型

CSRF 的成立条件只有一个：**浏览器会自动携带目标站点的 cookie，而攻击者不需要读到它**。

```text
受害者已登录 bank.com（浏览器里有 sid cookie）
    ↓
受害者打开攻击者页面 evil.com，页面里藏了：
    <form action="https://bank.com/api/transfer" method="POST">
      <input name="to" value="attacker"><input name="amount" value="10000">
    </form>
    <script>document.forms[0].submit()</script>
    ↓
浏览器向 bank.com 发 POST，并自动带上 sid cookie
    ↓
服务端看到合法会话 → 执行转账
```

关键点：攻击者**完全不需要知道** `userId`、也不需要读 cookie。所以"把身份藏在 httpOnly cookie 里"本身就是 CSRF 的成因，而只靠 cookie 无法防御。

### 本项目用两道防线

| 防线 | 机制 | 挡住的场景 |
| --- | --- | --- |
| `SameSite=Lax` | 跨站发起的 POST/PUT/…/XHR **不携带** cookie | 上面那个跨站表单 POST 直接失效（服务端看到的是无会话的陌生人） |
| CSRF Token | 请求必须带一个只有本站页面能读到的随机值，且与服务端 session 中的值恒定时间比对 | 浏览器不支持/被降级的 SameSite 场景；**同站但跨子域**的攻击（`a.example.com` 上的 XSS 能给 `example.com` 发同站请求，`SameSite` 不生效）；同站 XSS/第三方脚本冒充写操作 |

为什么两道都要：

- **`SameSite=Lax` 是浏览器行为**，它会随浏览器版本、降级策略、老旧客户端而变化，服务端无法强制。安全设计不应把全部赌注压在客户端的默认行为上。
- **`SameSite=Lax` 挡不住同站请求**。若站点有多个子域且其中一个被攻破（子域 XSS、子域接管的第三方服务），从该子域发起的请求是"同站"的，cookie 照常携带，此时唯一能挡住的就是 token。
- 反过来，**只有 token 没有 SameSite** 时，攻击者仍可通过跨站 `GET` 触发带 cookie 的读取型请求（虽然写操作有 token 保护，但信息泄露面更大）。两者互补。

### 为什么 token 要存在服务端 session 里

另一种常见做法是"双提交 Cookie"：把 token 同时放进 cookie 和请求头/body，服务端只比较两者是否相等，不需要服务端状态。它的致命缺陷是：**只要攻击者能往目标域写 cookie（子域 XSS、中间人注入、cookie 覆盖），就能把两边同时改成同一个值，校验形同虚设**。

本项目把 token 存在 `sess:<sid>` 里，客户端唯一能证明"我读到了 token"的方式就是真的收到了 `GET /csrf/token` 的响应体。而由于**同源策略**，跨站攻击者拿不到这个响应体。这就把 token 变成了一种"只有同源页面才有的凭证"。

代价是每个会话多存一个字段、且校验时必然要读一次 Redis（其实会话反正也要读）。对后台类系统完全值得。

### 携带方式与错误语义（实测）

| 请求 | 实测结果 |
| --- | --- |
| `POST /api/danger`（无 cookie、无 token） | `403 {"error":"CSRF token missing"}` |
| `POST /api/danger`（有 cookie，token = `bogus`） | `403 {"error":"CSRF token invalid"}` |
| `POST /api/danger` + `X-CSRF-Token: <正确值>` | `200 {"ok":true}` |
| `POST /api/danger` + body `{"_csrf":"<正确值>"}` | `200 {"ok":true}` |
| `DELETE /health`（有 cookie，无 token） | `403 {"error":"CSRF token missing"}` |
| `OPTIONS /api/danger`（CORS 预检） | `204`（安全方法放行，由 cors 处理） |
| `POST /api/danger`（登出后复用旧 token） | `403 {"error":"CSRF token missing"}`（session 已销毁，服务端没有 token 可比） |

注意最后一行：登出后旧 token **不是**被判为 `invalid`，而是 `missing`——因为服务端连"可比对的 token"都没有了。客户端据此就能判断"会话真的没了"，应该重新取 token 或跳登录页；若收到 `invalid`，则说明会话还在但 token 拿错了（多标签、缓存、或攻击），处理方式不同。

## 九、会话生命周期与 Redis 内容

### 状态机

```text
        ① 无 cookie / cookie 无效 / session 已过期
        │
        │  GET /csrf/token → 写入 csrfToken → 保存
        ▼
   ② 匿名但已有会话（Redis: sess:<sid> { csrfToken }）
        │                                   ▲
        │  POST /api/login（带合法 token）    │  POST /api/danger（带合法 token）
        ▼                                   │
   ③ 已登录（Redis: sess:<sid> { csrfToken, userId }）
        │
        │  POST /api/logout → destroy（DEL + 清 cookie）
        ▼
        ① 回到无会话

   旁路：SESSION_TTL 到期 / Redis 重启丢数据 / 换 SESSION_SECRET
        → 任意状态直接回到 ①
```

### Redis 里到底存了什么（实测）

登录后 `docker exec backend-redis redis-cli -a 123456 GET sess:<sid>` 的真实输出：

```json
{
  "cookie": {
    "originalMaxAge": 86400000,
    "expires": "2026-09-20T16:07:04.700Z",
    "secure": false,
    "httpOnly": true,
    "path": "/",
    "sameSite": "lax"
  },
  "csrfToken": "_8V3IUznckTT-JMxjOqHXEMSUJiPl5lJCXkMlZAlcoA",
  "userId": "u1"
}
```

可读出的信息：

- express-session 会把 cookie 的属性一并序列化进会话（`originalMaxAge` 就是 `SESSION_TTL * 1000`）。
- **`expires` 是绝对时间**，到期后即使 Redis 键还在（例如手工 `PERSIST` 过），express-session 也会判定会话过期。Redis 的 TTL 是同一时刻的第二道保险。
- `secure: false` 是因为当前跑在 `NODE_ENV=development`；`NODE_ENV=production` 下这里会是 `true`。
- 实测 `TTL sess:<sid>` = `86400`，与 `SESSION_TTL` 完全一致。

### 会话会在什么时候被销毁 / 失效

| 触发 | 效果 | 客户端感知 |
| --- | --- | --- |
| `POST /api/logout` → `session.destroy()` | Redis `DEL sess:<sid>` + `Set-Cookie: sid=; Expires=1970` | 立即退出登录（实测键数 1 → 0） |
| `SESSION_TTL` 到期 | Redis 自动删键；cookie 的 `Expires` 也已过 | 下次请求被当成新访客 |
| `SESSION_SECRET` 变更 | 旧 cookie 签名校验失败 → 被当成无 cookie | 全员掉线（见第十二节） |
| Redis 重启且未开持久化 | 数据丢失 | 全员掉线。根目录 `docker-compose.yml` 已开 `--appendonly yes` |
| 用户手工删 cookie / 换浏览器 | 服务端键还在但没人引用，靠 TTL 自然回收 | 掉线 |

### 为什么"空会话不落库"很关键

`saveUninitialized: false` 的实际效果（实测）：

- `GET /health` → `200`，**没有** `Set-Cookie`，Redis 键数不变。
- 无 cookie 的 `POST /api/danger` → `403`，Redis 键数不变（`before=3 after=3`）。
- 只有 `GET /csrf/token` 和已存在的会话被修改时才会写 Redis。

如果把 `saveUninitialized` 设成 `true`，上面每一个匿名请求都会在 Redis 里留下一个键，配合 `SESSION_TTL=86400`，攻击者只要刷 `/health` 就能把 Redis 内存吃满——这是一类典型的"零成本存储耗尽"攻击。

## 十二、安全边界与生产注意事项

### 已经覆盖的威胁

| 威胁 | 防护手段 |
| --- | --- |
| XSS 窃取会话凭证 | cookie `HttpOnly`，JS 读不到 sid |
| 伪造/篡改会话 id | cookie 带 HMAC 签名（`s:<sid>.<sig>`），伪造值会被判为无会话 |
| CSRF 借 cookie 发起写操作 | `SameSite=Lax` + 服务端 session 绑定的 CSRF Token 双重校验 |
| 时序侧信道猜 token | `timingSafeEqual` 恒定时间比较 |
| token 可预测 | `crypto.randomBytes(32)` 生成，非 `Math.random` |
| 匿名请求耗尽 Redis | `saveUninitialized: false`，空会话不落库 |
| 登出后会话残留 | `session.destroy()` 同时删 Redis 键与浏览器 cookie |
| 常见响应头漏洞 | `helmet()` 默认 CSP / `X-Content-Type-Options` 等 |
| 跨域携带凭证被滥用 | `credentials: true` 只与显式 `origin` 配合（生产需白名单） |

### 仍需注意（按优先级）

**① 登录时没有轮换 session id（会话固定攻击）**

实测：登录前后 `sid` 完全相同。这意味着攻击者若能事先把自己的 sid 塞进受害者的浏览器（子域 cookie 写入、URL 会话、中间人），诱导其登录后即可用同一个 sid 直接接管该会话。

标准做法是登录成功后 `regenerate`，顺带换掉 CSRF token：

```ts
authRoutes.post("/api/login", (req, res, next) => {
	// ...账号密码校验...
	const userId = "u1";
	req.session.regenerate((err) => {
		if (err) return next(err);
		req.session.userId = userId;
		req.session.csrfToken = generateCsrfToken(); // 可选：连 token 一起换
		req.session.save((err2) => {
			if (err2) return next(err2);
			res.json({ ok: true, csrfToken: req.session.csrfToken });
		});
	});
});
```

注意 `regenerate` 之后要重新写 `userId`，并且**必须把新的 `csrfToken` 告诉前端**（响应体带上，前端替换内存里的旧值），否则下一次写操作会 403。

**② `SESSION_SECRET` 无法平滑轮换**

`express-session` 的 `secret` 支持**数组**：数组第一项用于签名新 cookie，其余项用于校验旧 cookie。轮换时把新密钥插到第一位即可，存量会话不会掉线：

```ts
secret: [env.sessionSecret, ...env.sessionSecretOld],
```

直接替换单个密钥会让**所有** cookie 签名校验失败，表现为全站用户"莫名其妙被登出"。

**③ 会话没有"设备管理"能力**

`sess:<sid>` 的键里没有用户维度索引，所以无法列出"我的登录设备"、也无法"一键踢出所有设备"。要支持需要额外维护 `user:<userId>:sessions` 集合（登录时 `SADD`，登出时 `SREM`，踢人时遍历 `DEL`）。当前的登出只能登出自己这一个会话。

**④ 没有限流与登录失败控制**

`/api/login`、`/csrf/token`、以及所有写接口都无限流。至少在网关或应用层对 `/api/login` 加"按 IP + 账号"的失败计数与退避，否则密码爆破与 token 探测都没有成本。

**⑤ CORS 与 `trust proxy` 是生产硬要求**

```ts
// 生产：写成白名单，并按部署层数设置 trust proxy
app.use(
	cors({
		origin: ["https://admin.example.com"],
		credentials: true,
	}),
);
app.set("trust proxy", 1);
```

- `origin: true` 会回显任意来源，配合 `credentials: true` 等于对任何站点开放"带 cookie 的跨域请求"。开发方便，生产是漏洞。
- `trust proxy` 写错（层数与实际不符）会让 `secure` cookie 不生效，或被攻击者用伪造的 `X-Forwarded-Proto` 绕过；导致的现象通常是"登录成功但下一个请求就掉登录态"。

**⑥ Redis 强依赖与降级策略**

会话（含 CSRF token）全在 Redis，Redis 不可用时 `createApp()` 永远不会返回、端口不监听（实测行为）。这属于 fail-closed，是安全上可接受的选择，但要在部署层明确：

- 容器启动顺序：`depends_on: redis: { condition: service_healthy }`。
- 给进程加 readiness/liveness 探针，避免"进程在跑但没有监听"却仍被负载均衡分发流量。
- 若要"Redis 挂了仍能服务只读流量"，需要设计降级开关（通常不值得，因为会话没了等于所有人未登录）。

**⑦ 会话数据的边界**

`sess:<sid>` 里现在只有两个小字段，所以用 `express-session` 完全够。**不要把大对象塞进 session**（用户头像、权限树、长列表）：每个请求都要完整读一次并 JSON 反序列化，Redis 带宽和延迟都会上去。需要缓存大对象时用 `user:<id>` 这样的独立键，session 里只放 id。

**⑧ 代码层面的小瑕疵（不影响安全，建议清理）**

| 位置 | 问题 | 建议 |
| --- | --- | --- |
| `routes/auth.router.ts` | `if (!req.session)` 是死分支（express-session 总是注入该对象） | 可移除，或改为 `if (!req.session.userId)` 表达"未登录"的语义 |
| `routes/auth.router.ts` | `ok: "true"` 是字符串，与其他分支的布尔 `true` 不一致 | 统一为布尔 |
| `app.ts` | `res.json({ ok: true, useId: req.session.userId })` 拼写错误 | 改为 `userId` |
| `app.ts` | `/api/danger`、`/health` 直接写在 `app.ts` 里 | 示例路由可接受；真实业务应放 `routes/` |
| `middleware/csrf.ts` | 只读 `X-CSRF-Token` 与 body `_csrf`，不支持查询参数 | 保持现状即可——URL 里的 token 会进日志/Referer，反而是信息泄露源 |

**⑨ 审计与监控**

`403 CSRF token missing/invalid` 是廉价且高价值的告警信号：短时间内同一 IP 大量 `invalid`，通常意味着有人在探测；登出接口的 `destroy` 失败（当前只 `console.error`）也应上报。建议至少按 `timestamp / ip / ua / path / error` 落一条结构化日志。

## 十三、客户端对接要点

1. **跨域必须带凭证**：`fetch(url, { credentials: "include" })` 或 axios `withCredentials: true`。后端已配 `credentials: true`，前端不配就等于每次都拿不到会话。
2. **先取 token 再写**：应用启动（或首个写操作前）调一次 `GET /csrf/token`，把 token 放**内存变量**。

   ```ts
   let csrfToken: string | null = null;
   async function ensureToken() {
     if (!csrfToken) {
       const r = await fetch("/csrf/token", { credentials: "include" });
       csrfToken = (await r.json()).csrfToken;
     }
     return csrfToken;
   }
   async function write(url: string, body: unknown) {
     const token = await ensureToken();
     return fetch(url, {
       method: "POST",
       credentials: "include",
       headers: { "Content-Type": "application/json", "X-CSRF-Token": token! },
       body: JSON.stringify(body),
     });
   }
   ```

3. **不要存到 localStorage**：那等于把 token 暴露给任何 XSS 脚本。内存变量在页面关闭后自然消失，重新取一次的成本只是一个 GET。
4. **区分两种 403**：
   - `CSRF token missing` → 会话已失效（过期/登出/被清）或从未取过 token。`ensureToken()` 再取一次并**重试一次**请求。
   - `CSRF token invalid` → 会话还在但值不对。通常是多标签页互相覆盖、或前端缓存了旧 token；重新取一次并把全局变量刷新即可。**两种情况都不要跳登录页**，403 不等于未登录。
5. **`ensureToken()` 要做单飞去重**：页面初始化时并发发多个写请求，若各自都去 `GET /csrf/token`，虽然发放是幂等的（实测同一个 session 拿到同一个值），但仍会平白多出若干次往返。
6. **登出后清空内存 token**：`POST /api/logout` 成功后 `csrfToken = null`，下次登录会通过 `ensureToken()` 重新拿一份（属于新会话）。
7. **多标签页天然共享**：token 存在服务端会话里，与 cookie 绑定；同一浏览器的多个标签要么共享同一个 token，要么都会重新取到同一个值，不会互相失效（这是"发放幂等"带来的直接好处）。
8. **只有写操作需要 token**：`GET/HEAD/OPTIONS` 不用带，带了也无害。别在 `GET` 上做有副作用的操作，否则那道守卫会形同虚设。
9. **cookie 不需要也不能被前端读写**：它是 `HttpOnly`。不要写 `document.cookie = "sid=..."` 之类的代码——伪造的 sid 会因为签名校验失败而被当成陌生人（实测：返回一个全新会话）。
10. **登录响应要一并处理**：若按第十二节①做了 `regenerate`，登录响应体会多出新的 `csrfToken`，前端必须用它替换内存里的旧值，否则下一次写操作会 403。
