## 一、方案总览

核心是把"凭证"拆成两种性质完全不同的东西：**短期无状态凭证**和**长期有状态凭证**。

| | Access Token | Refresh Token |
| --- | --- | --- |
| 形态 | JWT（自包含、无状态） | 随机串 `crypto.randomBytes(48)` |
| 有效期 | 短（默认 15m） | 长（默认 7d） |
| 存放 | 客户端**内存**（JS 变量） | **httpOnly Cookie** |
| 传输 | `Authorization: Bearer <token>` | Cookie 自动携带 |
| 服务端校验 | `jwt.verify` + Redis 黑名单 `bl:<jti>` | Redis 查 `rt:<sha256>` |
| 主动吊销 | 拉黑 `jti`（TTL = 剩余寿命） | 直接删 Redis key |

选型理由：

- **Access Token 放内存而非 localStorage**：localStorage 可被任意 XSS 脚本读取，内存变量随页面关闭即消失，配合短有效期把泄露窗口压到最小。
- **Refresh Token 放 httpOnly Cookie**：JS 读不到，天然防 XSS 窃取；`SameSite=Strict` 挡跨站请求伪造；`Path=/auth` 让它只出现在刷新/登出请求上，业务请求根本不会带上它。
- **Refresh Token 用随机串 + Redis 而非 JWT**：JWT 的致命弱点是签发后无法主动作废。刷新令牌寿命长，必须可服务端吊销，所以走有状态存储。
- **Redis 只存 SHA-256 哈希，不存明文**：Redis 被拖库或做了备份泄露时，攻击者拿到的哈希无法反推 token，也无法直接用于登录。
- **轮换（Rotation）+ 复用检测（Reuse Detection）**：每次刷新都换发新 token 并作废旧 token；一旦检测到"已经轮换出去的旧 token 又被使用"，判定为 token 被盗，立即吊销整条令牌链。

一句话概括职责划分：JWT 负责"高频校验的性能"，Redis 负责"低频但必须能撤销的状态"。

## 四、Redis Key 设计

| Key | 类型 | Value | TTL | 用途 |
| --- | --- | --- | --- | --- |
| `rt:<sha256>` | string | `{"userId","familyId"}` | `REFRESH_TOKEN_EXPIRES_SEC` | **活跃** refresh token 主索引 |
| `rt:used:<sha256>` | string | `familyId` | 同上 | 已轮换出去的旧 token 标记，用于**复用检测** |
| `rt:family:<familyId>` | set | 该链上所有活跃 token 的 hash | 同上 | 批量吊销整条链（复用触发 / 登出全部设备） |
| `bl:<jti>` | string | `"1"` | Access Token 剩余寿命 | Access Token 黑名单（登出即时失效） |

设计要点：

- **`rt:` 与 `rt:used:` 必须成对存在**。只删旧 token 不留痕，就无法区分"攻击者复用一个消失的 token"和"正常用户用一个过期 token"，复用检测将失效。
- **`familyId` 是"一次登录"的身份**。每次登录生成一个新 `familyId`，同一设备后续轮换出的所有 token 共享它；多设备登录互不影响。
- **TTL 统一用 `refreshExpiresSec`**。family 集合也要设过期时间，否则长期运行会积累永不回收的 key。

## 五、核心实现

### 1. `.env` / `.env.example`

```env
# nodejs: node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
# openssl: openssl rand -base64 48 | tr -d '\n'
JWT_SECRET=replace-with-a-long-random-string
ACCESS_TOKEN_EXPIRES=15m
REFRESH_TOKEN_EXPIRES_SEC=604800
```

- `JWT_SECRET` 用 `openssl rand -base64 48` 或 `randomBytes(32).toString('base64url')` 生成，**不要**与 `SESSION_SECRET` 复用。
- `ACCESS_TOKEN_EXPIRES` 直接交给 `jsonwebtoken` 的 `expiresIn`，支持 `15m` / `1h` / `900` 等格式。
- `REFRESH_TOKEN_EXPIRES_SEC` 用**秒**，因为它同时是 Redis 的 `EX` 参数和 cookie 的 `maxAge/1000`。

`REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` 由根目录 `backend/.env` 提供（见第 2 节的多路径加载）。

### 2. `config/env.ts` —— 强类型环境变量 + 多路径 dotenv

> 因 `erasableSyntaxOnly` 禁用 `enum`，用 `as const` + 联合类型代替。

```ts
import { config } from "dotenv";
import { dirname, resolve } from "node:path";
import { fileURLToPath } from "node:url";

// 无论从哪个 CWD 启动，都从项目根目录加载 .env
const __dirname = dirname(fileURLToPath(import.meta.url));
config({
	path: [
		resolve(__dirname, "../../.env"),            // 子项目自己的 .env
		resolve(__dirname, "../../../../../.env"),   // backend/.env（Redis 配置）
	],
});

function getEnv(key: string, defaultValue?: string): string {
	const value = process.env[key];
	if (!value) {
		if (defaultValue !== undefined) return defaultValue;
		throw new Error(`环境变量 ${key} 未定义`);
	}
	return value;
}

export const env = {
	nodeEnv: getEnv("NODE_ENV", "development") as
		| "development"
		| "production"
		| "test",
	port: parseInt(getEnv("PORT", "3000"), 10),
	isProd: getEnv("NODE_ENV", "development") === "production",
	jwtSecret: getEnv("JWT_SECRET"),
	accessExpires: getEnv("ACCESS_TOKEN_EXPIRES"),
	refreshExpiresSec: parseInt(
		getEnv("REFRESH_TOKEN_EXPIRES_SEC", "604800"),
		10,
	),
	redis: {
		host: getEnv("REDIS_HOST", "localhost"),
		port: parseInt(getEnv("REDIS_PORT", "6379"), 10),
		password: getEnv("REDIS_PASSWORD", "") || undefined,
	},
} as const;
```

关键点：

- `dotenv` 的 `path` 传**数组**时会按顺序尝试加载，**先加载的不被后加载的覆盖**（`dotenv` 默认不覆盖已存在的 `process.env`）。所以子项目 `.env` 的 `JWT_SECRET` 优先，`backend/.env` 补齐 `REDIS_*`。
- `isProd` 用 `getEnv("NODE_ENV", "development")` 兜底，避免没配 `NODE_ENV` 时抛错导致进程起不来。
- 密码为空串时转 `undefined`，否则 node-redis 会带着空密码去 AUTH 而报错。

### 3. `redis/client.ts` —— Redis 单例 client

```ts
import { createClient, type RedisClientType } from "redis";
import { env } from "../config/env.ts";

let client: RedisClientType | null = null;

export async function getRedisClient(): Promise<RedisClientType> {
	if (client) return client;
	client = createClient({
		socket: { host: env.redis.host, port: env.redis.port },
		password: env.redis.password,
	}) as RedisClientType;

	client.on("error", (err) => {
		console.error("[Redis] client error", err);
	});
	await client.connect();
	return client;
}
```

要点：

- 模块级 `let client` 做单例，避免每次请求新建连接。
- 必须注册 `error` 事件监听，否则连接中断会变成 unhandled error 直接崩进程。
- `await client.connect()` 放在 `createApp()` 里（见第 8 节），启动即连，不要在第一个请求里懒连接。

### 4. `utils/token.ts` —— JWT 签发/校验 + 随机 token

```ts
import { createHash, randomBytes, randomUUID } from "node:crypto";
import jwt, { type SignOptions } from "jsonwebtoken";
import { env } from "../config/env.ts";

export type AccessTokenPayload = {
	userId: string;
	jti: string; // 唯一 id，用于黑名单
};

/** 生成随机 refresh token：48 字节 -> base64url */
export function generateRefreshToken(): string {
	return randomBytes(48).toString("base64url");
}

/** SHA-256 哈希，作为 Redis key（不明文存储） */
export function hashToken(token: string): string {
	return createHash("sha256").update(token).digest("hex");
}

export function newTokenId(): string {
	return randomUUID();
}

/** 签发 Access Token（JWT，无状态） */
export function signAccessToken(payload: AccessTokenPayload): string {
	return jwt.sign(payload, env.jwtSecret, {
		expiresIn: env.accessExpires as SignOptions["expiresIn"],
	});
}

/** 验证 Access Token，失败抛异常 */
export function verifyAccessToken(
	token: string,
): AccessTokenPayload & { exp: number } {
	return jwt.verify(token, env.jwtSecret) as AccessTokenPayload & {
		exp: number;
	};
}
```

要点：

- `randomBytes(48)` 给约 384 bit 熵，远超暴力破解可行范围；`base64url` 编码天然适合放进 cookie 和 URL，无需再转义。
- 刷新令牌用**密码学安全随机数**，不能用 `Math.random()` 或 `Date.now()` 拼接。
- `hashToken` 是 SHA-256 而非 bcrypt：这里的 token 本身就是高熵随机串，不存在字典攻击面，用快速哈希即可，且能在每次请求里无负担地调用。
- `jti` 用 `randomUUID()`，保证即使同一用户同一秒签发的 token 也能被独立拉黑。
- `expiresIn` 需断言成 `SignOptions["expiresIn"]`：`env` 是 `as const` 的字符串字面量类型，`@types/jsonwebtoken` 的 `expiresIn` 期望 `number | StringValue`，直接传会类型不兼容。

### 5. `services/tokenStore.ts` —— Redis token 存储（核心）

把散落的 key 拼接集中到 `K`（Key builder），避免手写 `"rt:" + hash` 时拼错导致安全漏洞。

```ts
import type { RedisClientType } from "redis";
import { env } from "../config/env.ts";

export type RefreshRecord = { userId: string; familyId: string };

const K = {
	active: (h: string) => `rt:${h}`,
	used: (h: string) => `rt:used:${h}`,
	family: (familyId: string) => `rt:family:${familyId}`,
	blacklist: (jti: string) => `bl:${jti}`,
};

export function createTokenStore(redis: RedisClientType) {
	const ttl = env.refreshExpiresSec;

	/** 登录：保存 refresh token + 建立 family 链 */
	async function saveRefresh(hash: string, rec: RefreshRecord) {
		const m = redis.multi();
		m.set(K.active(hash), JSON.stringify(rec), { EX: ttl });
		m.sAdd(K.family(rec.familyId), hash);
		m.expire(K.family(rec.familyId), ttl);
		await m.exec();
	}

	/** 轮换：旧 token 标记 used + 删 active；新 token 写 active + 加入 family */
	async function rotate(oldHash: string, newHash: string, rec: RefreshRecord) {
		const m = redis.multi();
		m.set(K.used(oldHash), rec.familyId, { EX: ttl }); // ① 标记旧 token 已用
		m.del(K.active(oldHash));                          // ② 删除旧 token 的有效记录
		m.sRem(K.family(rec.familyId), oldHash);           // ③ 从 family 集合移除旧 hash
		m.set(K.active(newHash), JSON.stringify(rec), { EX: ttl }); // ④ 写入新 token
		m.sAdd(K.family(rec.familyId), newHash);           // ⑤ 新 token 加入 family
		await m.exec();
	}

	async function getActive(hash: string): Promise<RefreshRecord | null> {
		const raw = await redis.get(K.active(hash));
		return raw ? (JSON.parse(raw) as RefreshRecord) : null;
	}

	/** 返回 familyId（若该 token 曾被轮换出，用于复用检测） */
	async function getUsed(hash: string): Promise<string | null> {
		return redis.get(K.used(hash));
	}

	/** 吊销整条 family（复用检测 / 登出全部设备） */
	async function revokeFamily(familyId: string) {
		const hashes = await redis.sMembers(K.family(familyId));
		if (hashes.length) await redis.del(hashes.map((h) => K.active(h)));
		await redis.del(K.family(familyId));
	}

	/** 仅吊销单个 token（当前设备登出） */
	async function revokeOne(hash: string, familyId: string) {
		const m = redis.multi();
		m.del(K.active(hash));
		m.sRem(K.family(familyId), hash);
		await m.exec();
	}

	/** Access Token 黑名单 */
	async function blacklistAccess(jti: string, ttlSec: number) {
		await redis.set(K.blacklist(jti), "1", { EX: ttlSec });
	}
	async function isBlacklisted(jti: string): Promise<boolean> {
		return (await redis.exists(K.blacklist(jti))) === 1;
	}

	return {
		saveRefresh,
		rotate,
		getActive,
		getUsed,
		revokeFamily,
		revokeOne,
		blacklistAccess,
		isBlacklisted,
	};
}

export type TokenStore = ReturnType<typeof createTokenStore>;
```

要点：

- **`multi()` 事务保证轮换的原子性**。`rotate` 里的 5 条命令要么全执行要么全不执行，避免出现"旧 token 已删、新 token 未写"的中间态把用户卡死在无法刷新的状态。
- **`revokeFamily` 用 `redis.del(array)`** 一次删掉整条链上所有活跃 token，而不是循环单删。
- **`revokeOne` 是"当前设备登出"**，只删自己那条，不影响同账号其他设备。
- **返回类型用 `Promise<boolean>` 而非 `Promise<Boolean>`**，避免装箱类型带来的无意义对象分配。

### 6. `middleware/auth.ts` —— Access Token 守卫

```ts
import type { RequestHandler } from "express";
import { verifyAccessToken } from "../utils/token.ts";
import type { TokenStore } from "../services/tokenStore.ts";

declare global {
	namespace Express {
		interface Request {
			userId?: string;
		}
	}
}

export function authGuard(store: TokenStore): RequestHandler {
	return async (req, res, next) => {
		const header = req.headers.authorization;
		if (!header?.startsWith("Bearer ")) {
			res.status(401).json({ error: "missing_token" });
			return;
		}
		try {
			const payload = verifyAccessToken(header.slice(7));
			if (await store.isBlacklisted(payload.jti)) {
				res.status(401).json({ error: "token_revoked" });
				return;
			}
			req.userId = payload.userId;
			next();
		} catch {
			res.status(401).json({ error: "invalid_or_expired_token" });
		}
	};
}
```

要点：

- **两级校验**：先验签（JWT 自身是否被篡改/过期），再查黑名单（是否被主动登出）。顺序不能反——查黑名单需要先拿到可信的 `jti`。
- `declare global` 扩展 `Express.Request`，让下游 handler 有 `req.userId` 的类型提示，无需再自己定义 `.d.ts`。
- 三段错误信息刻意区分：`missing_token`（没带）/ `invalid_or_expired_token`（坏了或过期）/ `token_revoked`（被拉黑）。客户端可据此分别处理。
- 用 `authGuard(store)` 工厂函数注入 `store`，而不是让中间件直接 import 单例，方便测试时替换。

### 7. `routes/auth.routes.ts` —— login / refresh / logout

```ts
import { Router, type Response } from "express";
import {
	signAccessToken,
	verifyAccessToken,
	generateRefreshToken,
	hashToken,
	newTokenId,
} from "../utils/token.ts";
import type { TokenStore } from "../services/tokenStore.ts";
import { env } from "../config/env.ts";

const COOKIE = "rt";

function setRefreshCookie(res: Response, token: string) {
	res.cookie(COOKIE, token, {
		httpOnly: true,
		secure: env.isProd,
		sameSite: "strict",
		path: "/auth", // 只有 /auth/* 能收到
		maxAge: env.refreshExpiresSec * 1000,
	});
}

export function authRoutes(store: TokenStore) {
	const r = Router();

	// ---------- POST /auth/login ----------
	r.post("/login", async (req, res) => {
		const { username, password } = req.body ?? {};
		// TODO: 替换为真实用户校验
		const user =
			username === "admin" && password === "123456" ? { id: "u_1" } : null;
		if (!user) {
			res.status(401).json({ error: "invalid_credentials" });
			return;
		}

		const refreshToken = generateRefreshToken();
		const familyId = newTokenId(); // 每次登录新建一条 family 链
		await store.saveRefresh(hashToken(refreshToken), {
			userId: user.id,
			familyId,
		});

		const accessToken = signAccessToken({
			userId: user.id,
			jti: newTokenId(),
		});
		setRefreshCookie(res, refreshToken);
		res.json({ accessToken });
	});

	// ---------- POST /auth/refresh ----------
	r.post("/refresh", async (req, res) => {
		const oldToken = req.cookies?.[COOKIE];
		if (!oldToken) {
			res.status(401).json({ error: "no_refresh_token" });
			return;
		}

		const oldHash = hashToken(oldToken);

		// 1) 检查是否是"已轮换出去的旧 token" -> 复用检测
		const usedFamilyId = await store.getUsed(oldHash);
		if (usedFamilyId) {
			// 旧 token 再次出现 = 被盗用，立即吊销整条 family 链
			await store.revokeFamily(usedFamilyId);
			res.status(401).json({ error: "reuse_detected" });
			return;
		}

		// 2) 查 active 表
		const rec = await store.getActive(oldHash);
		if (!rec) {
			res.status(401).json({ error: "invalid_refresh_token" });
			return;
		}

		// 3) 轮换：旧标记 used + 删 active；新 token 写入
		const newToken = generateRefreshToken();
		await store.rotate(oldHash, hashToken(newToken), rec);

		const accessToken = signAccessToken({
			userId: rec.userId,
			jti: newTokenId(),
		});
		setRefreshCookie(res, newToken);
		res.json({ accessToken });
	});

	// ---------- POST /auth/logout ----------
	r.post("/logout", async (req, res) => {
		const refreshToken = req.cookies?.[COOKIE];
		if (!refreshToken) {
			res.clearCookie(COOKIE, { path: "/auth" });
			res.json({ ok: true });
			return;
		}

		const hash = hashToken(refreshToken);
		const rec = await store.getActive(hash);

		if (rec) {
			await store.revokeOne(hash, rec.familyId); // 仅登出当前设备

			// 同时拉黑 Access Token（让当前 access 也立即失效）
			const authHeader = req.headers.authorization;
			if (authHeader?.startsWith("Bearer ")) {
				try {
					const payload = verifyAccessToken(authHeader.slice(7));
					const ttl = Math.max(payload.exp - Math.floor(Date.now() / 1000), 1);
					await store.blacklistAccess(payload.jti, ttl);
				} catch {
					/* access 已过期就不管了 */
				}
			}
		}
		res.clearCookie(COOKIE, { path: "/auth" });
		res.json({ ok: true });
	});

	return r;
}
```

要点：

- **`path: "/auth"` 是重要的收敛面**。浏览器只在请求 `/auth/*` 时携带该 cookie，业务接口的请求头里不会出现刷新令牌，减少暴露面。
- **`clearCookie` 的 `path` 必须与 `set` 时一致**（都是 `/auth`），否则浏览器不认，cookie 清不掉。
- **登录响应只返回 `accessToken`，不返回 refresh token**。refresh token 只通过 `Set-Cookie` 下发，前端 JS 永远拿不到它。
- **`refresh` 里的三步顺序不能变**：先查 `used`（复用检测）→ 再查 `active` → 最后 `rotate`。反过来会漏掉复用检测。
- **登出时顺手拉黑当前 access 的 `jti`**。JWT 无状态、验签仍会通过，不拉黑的话 access 会一直有效到自然过期（最长 15 分钟）。黑名单 TTL 取 `exp - now`，让 key 在 token 自然过期时自动消失，Redis 不会无限膨胀。
- `verifyAccessToken` 包在 `try/catch` 里：登出请求可能没带 Authorization，或带的是已过期 token，这些都不应影响登出成功。

### 8. `app.ts` —— 组装

```ts
import express, { type Express } from "express";

	const app = express();

	app.set("trust proxy", 1);
	app.use(helmet());
	app.use(cors({ origin: true, credentials: true }));
	app.use(express.json());

	});

}
```

要点：

- `getRedisClient()` 在 `createApp()` 内 `await`，启动期就完成连接，配置错误能立刻暴露。

## 六、完整流程与时序

1. **登录**：前端 `POST /auth/login` 提交账号密码 → 校验通过后生成 `refreshToken`（随机）和 `familyId`，把 `sha256(refreshToken)` 存进 Redis → 签发 access JWT → 通过 `Set-Cookie` 下发 refresh，body 只返回 `accessToken`。
2. **业务请求**：前端把 `accessToken` 放内存，请求时带 `Authorization: Bearer <token>` → `authGuard` 验签 + 查黑名单 → 放行并注入 `req.userId`。
3. **access 过期**：业务请求返回 401（`invalid_or_expired_token`），前端捕获后静默调用 `POST /auth/refresh`。
4. **刷新**：浏览器自动带上 refresh cookie → 后端查 `used` 表（复用检测）→ 查 `active` 表 → 轮换出新 refresh 并更新 cookie，同时签发新 access 返回给前端。
5. **登出**：前端 `POST /auth/logout` 带上当前 access → 后端删掉 Redis 里的 refresh 记录 + 拉黑 access 的 `jti` + 清 cookie。

```
浏览器                      Express                     Redis
  |  POST /auth/login          |                           |
  |--------------------------->|  saveRefresh(h1, family)  |
  |                            |-------------------------->|  SET rt:h1 ... / SADD family
  |<-- Set-Cookie: rt=A -------|                           |
  |<-- { accessToken: AT1 } ---|                           |
  |                            |                           |
  |  GET /api/me               |                           |
  |  Authorization: Bearer AT1 |                           |
  |--------------------------->|  verify(AT1)              |
  |                            |  EXISTS bl:<jti>  ------>|  (0)
  |<-- 200 { userId } ---------|                           |
  |                            |                           |
  |  POST /auth/refresh        |                           |
  |  Cookie: rt=A              |                           |
  |--------------------------->|  GET rt:used:hA  ------->|  (nil)
  |                            |  GET rt:hA       ------->|  (rec)
  |                            |  rotate(hA, hB)  ------->|  SET rt:used:hA / DEL rt:hA
  |                            |                           |  SET rt:hB / SADD family
  |<-- Set-Cookie: rt=B -------|                           |
  |<-- { accessToken: AT2 } ---|                           |
  |                            |                           |
  |  POST /auth/logout         |                           |
  |  Cookie: rt=B, Bearer AT2  |                           |
  |--------------------------->|  revokeOne(hB, family)--->|  DEL rt:hB / SREM family

  |<-- 200 { ok: true } -------|  clearCookie              |

  |  GET /api/me  Bearer AT2   |                           |
  |--------------------------->|  EXISTS bl:<jti>  ------>|  (1) -> 401 token_revoked
```

## 七、Refresh Token 轮换与复用检测

这是整套方案的安全核心，值得单独展开。

### 正常轮换

```
login    -> rt_A(active)
refresh  -> rt_A 标记 used + 删 active  -> rt_B(active)
refresh  -> rt_B 标记 used + 删 active  -> rt_C(active)
```

每次刷新都换发全新的 refresh，旧的立刻失效。攻击者即使拿到某个旧 token，可用的时间窗口也只有一个刷新周期。

### 复用检测

```
攻击者盗用了 rt_B（此时 rt_C 才是 active）：
  refresh(rt_B)
    -> GET rt:used:hB  命中，返回 familyId
    -> revokeFamily(familyId)  删掉 rt_C 等所有关联 token
    -> 401 reuse_detected
    -> 正常用户手里的 rt_C 也随之失效，被迫重新登录
```

这里的设计取舍很明确：**安全优先于体验**。宁可误杀正常用户一次（让他重登），也不能让被盗的令牌链继续可用。

### 为什么必须保留 `used` 表

如果轮换时直接删掉旧 token 的痕迹，就没法区分下面两种情况：

| 情况 | 现象 | 应处理方式 |
| --- | --- | --- |
| 攻击者重放一个**曾经有效**的 token | `active` 里查不到 | 判定被盗，**吊销整条链** |
| 正常用户用一个**从未存在/已过期很久**的 token | `active` 里查不到 | 直接 401，无需联动 |

`used` 表记录的正是"这个 token 曾经真实有效过"。命中它就等于确认发生了重放——这是唯一能区分上述两种情况的信号。

### 已知边界：并发刷新

若客户端因网络重试**并发**发了两次同一旧 token 的 `/refresh`，第二次会命中 `used` 触发吊销，把刚换出来的新 token 也一起作废。这是当前的保守策略。若要优化体验，可在 `used` 命中后引入一个短宽限窗口（例如 30 秒内同 token 返回同一批新 token），代价是安全强度下降。客户端侧更稳妥的做法是：**保证同一时刻只有一个刷新请求在飞行**（用一个 promise 做单飞/去重）。

## 八、登出实现

登出要做三件事，缺一不可：

| 动作 | 目的 | 代码 |
| --- | --- | --- |
| 删 Redis refresh 记录 | 让刷新令牌立即失效 | `store.revokeOne(hash, familyId)` |
| 拉黑 access `jti` | 让当前 access 立即失效（不必等自然过期） | `store.blacklistAccess(jti, ttl)` |
| 清浏览器 cookie | 防止下次请求继续带失效 cookie | `res.clearCookie(COOKIE, { path: "/auth" })` |

关键坑：

| 坑 | 说明 |
| --- | --- |
| 只删 Redis 不清 cookie | 浏览器仍带旧 cookie，每次刷新都 401 |
| `clearCookie` 的 `path` 与 `set` 不一致 | 浏览器不删 cookie，因为 cookie 是按 (name, domain, path) 唯一标识的 |
| 忘记拉黑 access | 登出后 access 仍能用到自然过期（最长 `ACCESS_TOKEN_EXPIRES`） |
| 黑名单 TTL 写成固定值 | 应取 `exp - now`，让 key 随 token 自然过期自动回收 |
| 登出接口强依赖 Bearer | access 可能已过期；登出应只依赖 refresh cookie，Bearer 是"可选加速失效" |

### 当前设备 vs 全部设备

- `revokeOne(hash, familyId)`：只登出当前设备，同账号其他设备的 token 不受影响。
- `revokeFamily(familyId)`：吊销整条链，用于"登出全部设备"或复用检测触发时。

要支持"登出全部设备"，需在登录时记录 `userId -> Set<familyId>` 的反向索引，登出全部时遍历所有 family 调用 `revokeFamily`。当前实现未包含这层索引。

## 十一、安全边界与生产注意事项

### 已经覆盖的威胁

| 威胁 | 防护手段 |
| --- | --- |
| XSS 窃取长期凭证 | refresh 在 httpOnly cookie，JS 读不到；access 在内存，短命 |
| CSRF 利用 cookie 触发刷新/登出 | `sameSite: "strict"` + `path: "/auth"` |
| refresh token 泄露后长期可用 | 短期轮换 + 复用检测吊销整条链 |
| Redis 数据泄露 | 只存 SHA-256 哈希，无法反推也无法直接使用 |
| 登出后 access 仍可用 | `bl:<jti>` 黑名单 + TTL 对齐剩余寿命 |
| JWT 篡改 | HMAC-SHA256 验签，`jwt.verify` 失败即 401 |

### 仍需注意

1. **密钥轮换**：当前只支持单个 `JWT_SECRET`，换密钥会让所有存量 access 立即失效（refresh 仍在，用户可无感刷新）。要做平滑轮换需支持 `kid` + 多密钥。
2. **算法固定**：`jwt.verify` 未显式限制 `algorithms`。虽然 `jsonwebtoken` v9 默认按密钥类型推导、不会接受 `none`，仍建议显式写 `{ algorithms: ["HS256"] }` 作为纵深防御。
3. **CORS 白名单**：`origin: true` 回显任意来源，仅适合开发。生产应换成明确的域名白名单。
4. **Redis 可用性**：鉴权强依赖 Redis（黑名单 + refresh 校验）。Redis 挂掉时受保护接口将无法校验黑名单——需要明确降级策略（fail-closed 更安全）。
5. **刷新接口限流**：`/auth/refresh` 是最值得被暴力尝试的端点，应在网关或应用层加速率限制。
6. **多设备与管理**：当前无 `userId -> familyId` 反向索引，"登出全部设备"和"查看登录设备列表"需要补这层。
7. **审计日志**：复用检测命中（`reuse_detected`）是高价值安全事件，建议记录 `userId` / `familyId` / IP / UA 并告警。

## 十二、客户端对接要点

1. **access 只存内存**，不要写 localStorage / sessionStorage。
2. **跨域请求必须带凭证**：`fetch(url, { credentials: "include" })` 或 axios `withCredentials: true`。只在 `/auth/*` 请求上需要，但因为 cookie 的 `path` 限制，带上也不会外泄。
3. **401 自动刷新要单飞去重**：多个请求同时 401 时，只发一次 `/auth/refresh`，其余等待同一个 promise 结果，避免并发刷新触发复用检测把自己踢下线。
4. **刷新失败即跳登录**：收到 `invalid_refresh_token` / `reuse_detected` 时，清空内存里的 access 并跳转登录页，不要重试。
5. **页面刷新后的静默续期**：access 在内存里，刷新页面就没了。应用启动时先调一次 `POST /auth/refresh` 试恢复会话，失败再进登录态。
6. **不要手动读 refresh cookie**：它是 httpOnly，本来就读不到；也不要在前端代码里试图设置它。
7. **登出要等服务端响应**：`/auth/logout` 负责吊销服务端状态，不能只在前端清内存（否则服务端 refresh 仍然有效）。
8. **`reuse_detected` 是安全信号**：若用户频繁遇到，说明有其他端在复用同一个旧 token，或客户端并发刷新有 bug，需排查而不是简单忽略。
