## 一、方案总览

核心是把"凭证"拆成两种性质完全不同的东西：**短期无状态凭证**和**长期有状态凭证**。

| | Access Token | Refresh Token |
| --- | --- | --- |
| 形态 | JWT（自包含、无状态） | 随机串 `crypto/rand` 48 字节 |
| 有效期 | 短（默认 15m） | 长（默认 720h = 30d） |
| 存放 | 客户端**内存**（JS 变量） | **HttpOnly Cookie** |
| 传输 | `Authorization: Bearer <token>` | Cookie 自动携带（`Path=/auth`） |
| 服务端校验 | 验签 + Redis 黑名单 `go:auth:bl:<jti>` | Redis 查 `go:auth:rt:<sha256>` |
| 主动吊销 | 拉黑 `jti`（TTL = 剩余寿命） | 直接删 Redis key / 吊销整条 family |

选型理由：

- **Access Token 放内存而非 localStorage**：localStorage 可被任意 XSS 脚本读取，内存变量随页面关闭即消失，配合短有效期把泄露窗口压到最小。
- **Refresh Token 放 HttpOnly Cookie**：JS 读不到，天然防 XSS 窃取；`SameSite=Strict` 挡跨站请求伪造；`Path=/auth` 让它只出现在刷新/登出请求上，业务请求根本不会带上它。
- **Refresh Token 用随机串 + Redis 而非 JWT**：JWT 的致命弱点是签发后无法主动作废。刷新令牌寿命长，必须可服务端吊销，所以走有状态存储。
- **Redis 只存 SHA-256 摘要，不存明文**：Redis 被拖库或做了备份泄露时，攻击者拿到摘要无法反推 token，也无法直接使用。
- **轮换（Rotation）+ 复用检测（Reuse Detection）**：每次刷新都换发新 token 并作废旧 token；一旦检测到"已经轮换出去的旧 token 又被使用"，判定为 token 被盗，立即吊销整条令牌链。
- **轮换用 Lua 脚本保证原子**：Go 这边比 Node 版多走了一步——把"查 used → 查 active → 写新 → 标旧 → 维护 family"五步放进单个 Lua 脚本，由 Redis 单线程串行执行，从根上消除并发刷新的 TOCTOU 竞态。

一句话概括职责划分：JWT 负责"高频校验的性能"，Redis 负责"低频但必须能撤销的状态"。

## 四、Redis Key 设计

所有键都带 `KEY_PREFIX`（默认 `go:auth:`），与同仓库 Node 版的裸 `rt:` 前缀隔离，两套实现可以共用同一个 Redis 实例而不互相污染。

| Key | 类型 | Value | TTL | 用途 |
| --- | --- | --- | --- | --- |
| `go:auth:rt:<sha256>` | hash | `uid`、`fid` | `REFRESH_TTL` | **活跃** refresh token 主索引 |
| `go:auth:rt:used:<sha256>` | string | `fid` | `REFRESH_TTL` | 已轮换出去的旧 token 标记，用于**复用检测** |
| `go:auth:rt:family:<fid>` | set | 该链上活跃 token 的 hash | `REFRESH_TTL`，轮换时续期 | 批量吊销整条链（复用触发 / 登出全部设备） |
| `go:auth:bl:<jti>` | string | `"1"` | Access Token 剩余寿命 | Access Token 黑名单（登出即时失效） |

设计要点：

- **`rt:` 与 `rt:used:` 必须成对存在**。只删旧 token 不留痕，就无法区分"攻击者复用一个消失的 token"和"正常用户用一个过期 token"，复用检测将失效。
- **active 用 Hash 而不是 JSON 字符串**（与 Node 版的差异之一）：轮换时可以只读 `fid` 一个字段（`HMGET`），不必反序列化整个记录；Lua 里也用 `HSET` 直接写两个字段。
- **`fid` 是"一次登录"的身份**。每次登录生成一个新 `fid`，同一设备后续轮换出的所有 token 共享它；多设备登录互不影响。
- **TTL 统一用 `REFRESH_TTL`**。family 集合也要设过期时间，否则长期运行会积累永不回收的 key。
- **黑名单 TTL = access 的剩余寿命**，用完自动回收，不会随登出次数无限增长。

## 五、核心实现

### 1. `.env` / `.env.example`

```env
APP_ENV=development
PORT=3001                    # 别用 3000，Node 版占着

REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_PASSWORD=please-change-me
REDIS_DB=0
KEY_PREFIX=go:auth:          # 和 Node 版共用 Redis 时必须不同前缀

# openssl rand -base64 48
JWT_SECRET=please-change-me-at-least-32-bytes-long
JWT_ISSUER=backend-api
JWT_AUDIENCE=backend-web

ACCESS_TTL=15m
REFRESH_TTL=720h

COOKIE_SECURE=false          # 生产 https 必须 true
COOKIE_DOMAIN=
```

注意点：

- `JWT_SECRET` 用 `openssl rand -base64 48` 生成，**不要**与 `SESSION_SECRET` 复用。
- `ACCESS_TTL` / `REFRESH_TTL` 是 Go 的 `time.ParseDuration` 格式（`15m` / `720h`），不是秒数。Node 版用秒是因为要给 Redis 的 `EX` 和 cookie 的 `maxAge` 共用，Go 这边 `time.Duration` 一路传到底，只在进 Redis 前用 `int64(d.Seconds())` 转一次。
- `.env` 里 `KEY_PREFIX=go:auth:` 后面那段是行内注释——`godotenv` 会把「空白 + `#`」之后的部分当注释剥掉，所以解析结果是干净的 `go:auth:`。**但只对"空白 + `#`"这种写法生效**，`KEY=a#b` 不会被截断。
- `.gitignore` **当前是空文件**，而 `.env` 里放的是真实 `JWT_SECRET`。这个必须补上（见第十四章）。

### 2. `config/config.go` —— 强类型配置 + 启动期校验

```go
type Config struct {
	Env  string
	Port string

	RedisAddr     string
	RedisPassword string
	RedisDb       int
	KeyPrefix     string

	JWTSecret   []byte
	JWTIssuer   string
	JWTAudience string

	AccessTTL  time.Duration
	RefreshTTL time.Duration

	CookieSecure bool
	CookieDomain string
}

func (c *Config) IsProd() bool { return c.Env == "production" }

func Load() *Config {
	_ = godotenv.Load()

	c := &Config{
		Env:  env("APP_ENV", "development"),
		Port: env("PORT", "3001"),

		RedisAddr:     net.JoinHostPort(env("REDIS_HOST", "127.0.0.1"), env("REDIS_PORT", "6379")),
		RedisPassword: os.Getenv("REDIS_PASSWORD"),
		RedisDb:       envInt("REDIS_DB", 0),
		KeyPrefix:     env("KEY_PREFIX", "go:auth:"),
		JWTSecret:     []byte(os.Getenv("JWT_SECRET")),
		JWTIssuer:     env("JWT_ISSUER", "backend-api"),
		JWTAudience:   env("JWT_AUDIENCE", "backend-web"),
		AccessTTL:     envDur("ACCESS_TTL", 15*time.Minute),
		RefreshTTL:    envDur("REFRESH_TTL", 30*24*time.Hour),
		CookieDomain:  os.Getenv("COOKIE_DOMAIN"),
	}

	c.CookieSecure = envBool("COOKIE_SECURE", c.IsProd())

	if len(c.JWTSecret) < 32 {
		log.Fatal("config: JWT_SECRET 至少 32 字节，用 openssl rand -base64 48 生成")
	}

	if c.RefreshTTL <= c.AccessTTL {
		log.Fatal("config: REFRESH_TTL 必须大于 ACCESS_TTL")
	}

	return c
}
```

配套的 `env` / `envInt` / `envBool` / `envDur` 四个小工具函数，语义都是"读不到或解析失败就用默认值"：

```go
func env(k, def string) string {
	if v := os.Getenv(k); v != "" {
		return v
	}
	return def
}

func envDur(k string, def time.Duration) time.Duration {
	if v, err := time.ParseDuration(os.Getenv(k)); err == nil {
		return v
	}
	return def
}
```

要点：

- **启动期校验优于运行期报错**：`JWT_SECRET` 太短、`REFRESH_TTL <= ACCESS_TTL` 这类配置错误在进程启动时就 `log.Fatal`，而不是等到第一个登录请求才炸。
- **`RedisAddr` 用 `net.JoinHostPort` 拼**，而不是 `host + ":" + port`。IPv6 地址（`::1`）手拼会得到 `::1:6379` 这种非法格式。
- **`JWT_SECRET` 用 `[]byte` 存**：`jwt.SignedString` 和 keyfunc 都吃 `[]byte`，存成 `[]byte` 可以少一次转换，也避免每次回读环境变量。
- **`CookieSecure` 默认跟随环境**：`APP_ENV=production` 时自动为 true，本地开发默认 false（否则 http 下浏览器不会存 cookie）。
- 文件底部还有一个**未被调用**的 `loadEnvFiles()` / `findUpAll()`：设计意图是按 `.env` → `.env.<APP_ENV>` → `.env.local` 的优先级，并从当前目录向上逐级查找父目录的 `.env`（Node 版就用了多路径加载）。目前 `Load()` 走的是单文件 `godotenv.Load()`。要么接上，要么删掉（见第十四章）。

### 3. `redis/client.go` —— Redis 客户端

```go
package redisclient

// UniversalClient 让同一份代码既能连单机也能连 Cluster
func New(cfg *config.Config) (redis.UniversalClient, error) {
	rdb := redis.NewClient(&redis.Options{
		Addr:         cfg.RedisAddr,
		Password:     cfg.RedisPassword,
		DB:           cfg.RedisDb, // Cluster 模式下必须为 0
		PoolSize:     20,
		MinIdleConns: 5,
		DialTimeout:  3 * time.Second,
		ReadTimeout:  2 * time.Second,
		WriteTimeout: 2 * time.Second,
	})
	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()
	if err := rdb.Ping(ctx).Err(); err != nil {
		_ = rdb.Close()
		return nil, err
	}
	return rdb, nil
}
```

要点：

- **返回接口 `redis.UniversalClient`**，它同时被 `*Client`（单机）、`*ClusterClient`（集群）、`*Ring`（分片）实现。`services.TokenStore` 只依赖接口，将来换集群不用改存储层。
- **启动时就 `Ping`**，连不上直接返回错误，让 `main` 在启动阶段退出，而不是把故障推迟到第一个请求。
- **显式配 `DialTimeout` / `ReadTimeout` / `WriteTimeout`**：默认值在 Redis 半死（连接建立但无响应）时会挂很久，鉴权路径上的超时必须收紧，好让 fail-closed 快速生效。
- **`PoolSize` / `MinIdleConns`** 按鉴权流量调。每个受保护请求都会打一次 Redis（黑名单检查），连接池太小会在这里排队。

### 4. `utils/token.go` —— JWT 签发/校验 + 随机 token

```go
type AccessClaims struct {
	UserID string `json:"uid"`
	jwt.RegisteredClaims
}

// 48 字节随机 → 384bit 熵
func NewRefreshToken() (string, error) {
	b := make([]byte, 48)
	if _, err := rand.Read(b); err != nil {
		return "", err
	}
	return "v1." + base64.RawURLEncoding.EncodeToString(b), nil
}

// 直接用 SHA-256 摘要即可：原文是高熵随机串，不存在字典攻击。
// 不要用 bcrypt/argon2，会白白给每次刷新加几十毫秒。
func HashRefreshToken(token string) string {
	sum := sha256.Sum256([]byte(token))
	return hex.EncodeToString(sum[:])
}

// 签发 Access Token：jti 用于黑名单，sub/uid 是业务身份
func NewAccessToken(cfg *config.Config, userId string) (raw, jti string, expiresAt time.Time, err error) {
	now := time.Now()
	jti = uuid.New().String()
	expiresAt = now.Add(cfg.AccessTTL)

	claims := AccessClaims{
		UserID: userId,
		RegisteredClaims: jwt.RegisteredClaims{
			ID:        jti,
			Subject:   userId,
			Issuer:    cfg.JWTIssuer,
			Audience:  jwt.ClaimStrings{cfg.JWTAudience},
			IssuedAt:  jwt.NewNumericDate(now),
			NotBefore: jwt.NewNumericDate(now),
			ExpiresAt: jwt.NewNumericDate(expiresAt),
		},
	}
	raw, err = jwt.NewWithClaims(jwt.SigningMethodHS256, claims).SignedString(cfg.JWTSecret)
	return raw, jti, expiresAt, err
}

// 校验端必须锁定算法白名单，否则存在 alg 混淆 / alg=none 绕过
func ParseAccessToken(cfg *config.Config, raw string) (*AccessClaims, error) {
	claims := new(AccessClaims)
	_, err := jwt.NewParser(
		jwt.WithValidMethods([]string{jwt.SigningMethodHS256.Alg()}),
		jwt.WithIssuer(cfg.JWTIssuer),
		jwt.WithAudience(cfg.JWTAudience),
		jwt.WithExpirationRequired(),
		jwt.WithLeeway(30*time.Second),
	).ParseWithClaims(raw, claims, func(t *jwt.Token) (any, error) {
		return cfg.JWTSecret, nil
	})

	if err != nil {
		return nil, err
	}
	if claims.UserID == "" {
		return nil, errors.New("token missing uid")
	}
	return claims, nil
}

// 登出时用：签名照样验，但不验过期，这样才能拿到已过期 access 的 jti 去拉黑
func ParseAccessTokenIgnoringExpiry(cfg *config.Config, raw string) (*AccessClaims, error) {
	claims := new(AccessClaims)
	_, err := jwt.NewParser(
		jwt.WithValidMethods([]string{jwt.SigningMethodHS256.Alg()}),
		jwt.WithoutClaimsValidation(),
	).ParseWithClaims(raw, claims, func(t *jwt.Token) (any, error) {
		return cfg.JWTSecret, nil
	})
	if err != nil {
		return nil, err
	}
	return claims, nil
}

func BearerToken(header string) (string, bool) {
	const prefix = "Bearer "
	if len(header) <= len(prefix) || !strings.EqualFold(header[:len(prefix)], prefix) {
		return "", false
	}
	return strings.TrimSpace(header[len(prefix):]), true
}
```

要点：

- **`crypto/rand` 而非 `math/rand`**：48 字节给约 384 bit 熵，远超暴力破解可行范围。`RawURLEncoding` 不带 padding，适合放进 cookie。
- **`v1.` 前缀**是给 token 格式留版本位：将来换格式（比如改成 `fid.随机串`）时可以按前缀分流识别，而不是靠长度猜。
- **`HashRefreshToken` 用 SHA-256 而非 bcrypt/argon2**：这里的 token 本身就是高熵随机串，不存在字典攻击面，用快速哈希即可，且能在每次请求里无负担地调用。
- **`WithValidMethods` 是必须的**：不锁算法白名单，攻击者可以把 header 的 `alg` 改成 `none`，或从 RS256 换成 HS256（拿公钥当 HMAC 密钥）来绕过验签。这是 JWT 最经典的坑。
- **`WithIssuer` / `WithAudience` / `WithExpirationRequired`**：把 `iss`、`aud`、`exp` 三个声明变成强制校验项，防止把别的服务签发的 token 拿来用，也防止签出永不过期的 token。
- **`WithLeeway(30s)`**：多实例部署时机器间时钟不可能完全一致，留 30 秒容差，避免"A 机器刚签发的 token 在 B 机器上被判 not yet valid"。
- **`ParseAccessTokenIgnoringExpiry` 仍验签名**：`WithoutClaimsValidation` 只跳过 `exp` / `nbf` / `iat` 的时间校验，签名和算法白名单照验，所以攻击者无法用它伪造 jti 去污染黑名单。
- **`BearerToken` 用 `EqualFold`**：HTTP 头里的 scheme 大小写不敏感，`bearer xxx` 也应该认。

**登录：保存 refresh token + 建立 family 链**

```go
func (s *TokenStore) SaveRefresh(ctx context.Context, hash, userID, familyID string) error {
	tx := s.rdb.TxPipeline()
	tx.HSet(ctx, s.activeKey(hash), "uid", userID, "fid", familyID)
	tx.Expire(ctx, s.activeKey(hash), s.refreshTTL)
	tx.SAdd(ctx, s.familyKey(familyID), hash)
	tx.Expire(ctx, s.familyKey(familyID), s.refreshTTL)
	_, err := tx.Exec(ctx)
	return err
}
```

**读记录 / 查复用标记**

```go
// 注意：这里只读不写，读到的 fid 对该 token 是恒定的（同一随机串永远映射同一条链），
// 所以"先读 fid，再用脚本原子改"不存在正确性问题。
func (s *TokenStore) ActiveRecord(ctx context.Context, hash string) (*RefreshRecord, error) {
	vals, err := s.rdb.HMGet(ctx, s.activeKey(hash), "uid", "fid").Result()
	if err != nil {
		return nil, err
	}
	if len(vals) != 2 || vals[0] == nil || vals[1] == nil {
		return nil, ErrNotFound
	}
	return &RefreshRecord{UserID: vals[0].(string), FamilyID: vals[1].(string)}, nil
}

// 返回该 token 曾经所属的 family（只对"已被轮换出去"的 token 有值）
func (s *TokenStore) UsedFamily(ctx context.Context, hash string) (string, error) {
	fid, err := s.rdb.Get(ctx, s.usedKey(hash)).Result()
	if errors.Is(err, redis.Nil) {
		return "", nil
	}
	return fid, err
}
```

**轮换：一次 Lua 调用做完所有判断和写入**

```go
func (s *TokenStore) Rotate(ctx context.Context, oldHash, newHash, userID, familyID string) (RotateResult, error) {
	ttl := int64(s.refreshTTL.Seconds())
	res, err := s.rotate.Run(ctx, s.rdb, []string{
		s.activeKey(oldHash),  // KEYS[1] = rt:<oldHash>
		s.usedKey(oldHash),    // KEYS[2] = rt:used:<oldHash>
		s.activeKey(newHash),  // KEYS[3] = rt:<newHash>
		s.familyKey(familyID), // KEYS[4] = rt:family:<fid>
	}, newHash, oldHash, userID, familyID, ttl).Int64()
	if err != nil {
		return RotateInvalid, err
	}
	return RotateResult(res), nil
}
```

**吊销与黑名单**

```go
// 当前设备登出
func (s *TokenStore) RevokeOne(ctx context.Context, hash, familyID string) error {
	tx := s.rdb.TxPipeline()
	tx.Del(ctx, s.activeKey(hash))
	tx.SRem(ctx, s.familyKey(familyID), hash)
	_, err := tx.Exec(ctx)
	return err
}

// 吊销整条链：复用检测触发时调用。used 标记故意保留，这样被盗的旧 token 再次出现仍能被识别。
func (s *TokenStore) RevokeFamily(ctx context.Context, familyID string) (int64, error) {
	hashes, err := s.rdb.SMembers(ctx, s.familyKey(familyID)).Result()
	if err != nil {
		return 0, err
	}
	keys := make([]string, 0, len(hashes)+1)
	for _, h := range hashes {
		keys = append(keys, s.activeKey(h))
	}
	keys = append(keys, s.familyKey(familyID))
	return s.rdb.Del(ctx, keys...).Result()
}

// 黑名单只存到 access 自然过期为止，过期后 key 自己消失，不会无限增长
func (s *TokenStore) BlacklistAccess(ctx context.Context, jti string, ttl time.Duration) error {
	if ttl < 0 {
		return nil
	}
	return s.rdb.Set(ctx, s.blacklistKey(jti), "1", ttl).Err()
}

func (s *TokenStore) IsBlacklisted(ctx context.Context, jti string) (bool, error) {
	n, err := s.rdb.Exists(ctx, s.blacklistKey(jti)).Result()
	if err != nil {
		return false, err
	}
	return n == 1, nil
}
```

要点：

- **为什么用 Lua 而不是 `TxPipeline`**：MULTI/EXEC 只保证"这几条命令一起执行"，但它**不能把读结果喂给后面的写**。而轮换必须先读（这个 token 有没有被用过、还在不在）再按结果决定怎么写，这个"读-判断-写"必须整体原子。Lua 脚本在 Redis 里是单线程串行执行的，天然满足。
- **`redis.NewScript` 会自动 EVALSHA 并按需回退到 EVAL**：脚本首次执行后缓存在 Redis 端，后续只传 sha1，开销接近普通命令。
- **先读 fid、再跑脚本不会破坏原子性**：`rt:<hash>` → `fid` 这个映射对这个随机 token 是恒定的（同一个随机串永远只属于一条链）。真正需要原子的"检查 used + 检查 active + 改状态"全在脚本里。这个设计还有个额外好处——key 名在调脚本前就已确定，所以将来上 Redis Cluster 时可以直接给同族的键加 hash tag（见第十一章）。
- **`SaveRefresh` 和 `RevokeOne` 用 `TxPipeline` 就够了**：这两处没有"读-判断-写"的依赖，只是要把多条命令打包，MULTI/EXEC 足矣。
- **`RevokeFamily` 用一次性 `DEL keys...`** 删掉整条链上所有活跃 token，而不是循环单删，减少 RTT。
- **`RevokeFamily` 故意不删 `used` 标记**：删掉的话，被盗的旧 token 之后再来就只会得到"无效 token"，无法触发复用检测，也追溯不到事件。
- **`UsedFamily` 把 `redis.Nil` 翻译成 `("", nil)`**：在 Go 里 `Get` 一个不存在的 key 返回的是错误而不是空值。不显式处理 `redis.Nil`，调用方就没法区分"key 不存在"和"Redis 挂了"——前者是正常的业务分支，后者是需要 fail-closed 的故障。
- **`ActiveRecord` 用 `HMGet` 只取需要的两个字段**，并校验 `len(vals)` 与 `nil`（`HMGet` 对不存在的字段返回 `nil`，直接类型断言会 panic）。

### 6. `middleware/auth.go` —— Access Token 守卫

```go
func Auth(cfg *config.Config, store *services.TokenStore) gin.HandlerFunc {
	return func(ctx *gin.Context) {
		raw, ok := utils.BearerToken(ctx.GetHeader("Authorization"))
		if !ok {
			ctx.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "missing_token"})
			return
		}

		claims, err := utils.ParseAccessToken(cfg, raw)
		if err != nil {
			code := "invalid_token"
			if errors.Is(err, jwt.ErrTokenExpired) {
				code = "token_expired" // 让前端区分"该刷新了"和"token 是假的"
			}
			ctx.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": code})
			return
		}

		revoked, err := store.IsBlacklisted(ctx.Request.Context(), claims.ID)
		if err != nil {
			// fail-closed：Redis 挂了宁可拒绝，绝不放行可能已登出的 token
			ctx.AbortWithStatusJSON(http.StatusServiceUnavailable, gin.H{"error": "auth_backend_unavailable"})
			return
		}
		if revoked {
			ctx.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "token_revoked"})
			return
		}

		ctx.Set(CtxUserID, claims.UserID)
		ctx.Set(CtxTokenID, claims.ID)
		ctx.Next()
	}
}
```

> 注：仓库当前源码在这一处漏写了 `return`（`AbortWithStatusJSON` 之后仍会走到 `ctx.Next()`）。行为仍然正确——gin 的 `Abort()` 会把 handler 索引推到 `abortIndex`，`Next()` 变成空操作——但显式写 `return` 更稳妥。详见第十四章第 3 条。

要点：

- **两级校验**：先验签（JWT 自身是否被篡改/过期），再查黑名单（是否被主动登出）。顺序不能反——查黑名单需要先拿到可信的 `jti`。
- **fail-closed**：Redis 查询失败返回 **503** 而不是放行。鉴权路径上"不确定"必须按"拒绝"处理；如果这里放行，Redis 一挂就等于所有已登出的 token 全部复活。
- **错误信息刻意区分几段**：`missing_token`（没带）/ `token_expired`（过期，前端应该去刷新）/ `invalid_token`（坏了）/ `token_revoked`（被拉黑，应该直接跳登录）。客户端据此决定是"静默刷新"还是"强制登出"。
- **用工厂函数 `Auth(cfg, store)` 注入依赖**，而不是让中间件直接 import 全局单例，便于测试时替换。
- 中间件通过 `ctx.Set(CtxUserID, ...)` 把身份传给下游，`routes.Me` 用 `c.Get(middleware.CtxUserID)` 取回。常量集中在 `middleware` 包里，避免两边字符串写错却不报错。

```go
func (h *AuthHandler) Refresh(c *gin.Context) {
	raw, err := c.Cookie(refreshCookieName)
	if err != nil || raw == "" {
		c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "no_refresh_token"})
		return
	}

	ctx := c.Request.Context()
	oldHash := utils.HashRefreshToken(raw)

	rec, err := h.store.ActiveRecord(ctx, oldHash)
	if err != nil {
		if !errors.Is(err, services.ErrNotFound) {
			c.AbortWithStatusJSON(http.StatusServiceUnavailable, gin.H{"error": "auth_backend_unavailable"})
			return
		}
		// 活跃记录不在：查是不是"已被轮换出去的旧 token"
		if fid, _ := h.store.UsedFamily(ctx, oldHash); fid != "" {
			if _, err := h.store.RevokeFamily(ctx, fid); err != nil {
				slog.Error("revoke family", "err", err)
			}
			slog.Warn("refresh token reuse detected", "family", fid)
			h.clearRefreshCookie(c)
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "refresh_reuse_detected"})
			return
		}
		h.clearRefreshCookie(c)
		c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "invalid_refresh_token"})
		return
	}

	// 先签发 access 再轮换：签名失败时不会白白消耗掉客户端唯一的 refresh token
	access, _, _, err := utils.NewAccessToken(h.cfg, rec.UserID)
	// ... 500 internal_error
	newRaw, err := utils.NewRefreshToken()
	// ... 500 internal_error

	res, err := h.store.Rotate(ctx, oldHash, utils.HashRefreshToken(newRaw), rec.UserID, rec.FamilyID)
	if err != nil {
		c.AbortWithStatusJSON(http.StatusServiceUnavailable, gin.H{"error": "auth_backend_unavailable"})
		return
	}

	switch res {
	case services.RotateReused:
		// 脚本内发现该 token 已被轮换过（并发刷新或重放），这里做兜底吊销
		if _, err := h.store.RevokeFamily(ctx, rec.FamilyID); err != nil {
			slog.Error("revoke family", "err", err)
		}
		slog.Warn("refresh token reuse detected", "family", rec.FamilyID, "user", rec.UserID)
		h.clearRefreshCookie(c)
		c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "refresh_reuse_detected"})
		return
	case services.RotateInvalid:
		h.clearRefreshCookie(c)
		c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "invalid_refresh_token"})
		return
	}

	h.setRefreshCookie(c, newRaw)
	c.JSON(http.StatusOK, gin.H{
		"accessToken": access,
		"tokenType":   "Bearer",
		"expiresIn":   int(h.cfg.AccessTTL.Seconds()),
	})
}
```

**登出**：

```go
func (h *AuthHandler) Logout(c *gin.Context) {
	ctx := c.Request.Context()

	if raw, err := c.Cookie(refreshCookieName); err == nil && raw != "" {
		hash := utils.HashRefreshToken(raw)
		if rec, err := h.store.ActiveRecord(ctx, hash); err == nil {
			if err := h.store.RevokeOne(ctx, hash, rec.FamilyID); err != nil {
				slog.Error("revoke refresh", "err", err)
			}
		}
	}

	// 让当前 access 也立刻失效；如果接受"access 最长 15 分钟后自然过期"，这段可以删掉
	if raw, ok := utils.BearerToken(c.GetHeader("Authorization")); ok {
		if claims, err := utils.ParseAccessTokenIgnoringExpiry(h.cfg, raw); err == nil && claims.ExpiresAt != nil {
			if ttl := time.Until(claims.ExpiresAt.Time); ttl > 0 {
				if err := h.store.BlacklistAccess(ctx, claims.ID, ttl); err != nil {
					slog.Error("blacklist access", "err", err)
				}
			}
		}
	}

	h.clearRefreshCookie(c)
	c.JSON(http.StatusOK, gin.H{"ok": true})
}
```

要点：

- **登录响应只返回 `accessToken`，不返回 refresh token**。refresh token 只通过 `Set-Cookie` 下发，前端 JS 永远拿不到它。
- **`Path="/auth"` 是重要的收敛面**。浏览器只在请求 `/auth/*` 时携带该 cookie，业务接口的请求头里不会出现刷新令牌，减少暴露面。
- **`clearRefreshCookie` 的属性必须与 `set` 完全一致**（`Path` / `Domain` / `Secure` / `SameSite`）。cookie 在浏览器里按 (name, domain, path) 唯一标识，少一个 `Domain` 都可能导致清不掉——表现为"登出后仍带着旧 cookie 反复刷新，一直 401"。
- **`Refresh` 的分支顺序不能变**：先查 `active`（拿到 fid 才能拼 family key）→ 不在就查 `used` 判断是"重放"还是"单纯无效" → 最后 `rotate`。反过来会漏掉复用检测。
- **先签 access、再轮换 refresh**：如果签名失败就把客户端唯一有效的 refresh token 消耗掉了，用户只能重新登录。顺序调换后，失败时 refresh 仍然可用。
- **`rotate` 返回 `RotateReused` 时再做一次 `RevokeFamily` 兜底**：脚本本身只返回状态码、不做吊销（脚本里只处理 KEYS 里已知的 4 个键，而 family 集合的成员数量不定），吊销放在 Go 侧执行。
- **登出时顺手拉黑当前 access 的 `jti`**。JWT 无状态、验签仍会通过，不拉黑的话 access 会一直有效到自然过期（最长 `ACCESS_TTL`）。黑名单 TTL 取 `time.Until(exp)`，让 key 在 token 自然过期时自动消失，Redis 不会无限膨胀。
- **登出对 refresh cookie 是"尽力而为"**：拿不到 cookie 或记录已不存在也照样返回 `200 {"ok":true}`。登出必须幂等——用户点两次登出、或 cookie 已被清掉，都不该报错。
- **`ParseAccessTokenIgnoringExpiry` 包在 `if err == nil` 里**：登出请求可能没带 Authorization，或带的是已过期/已损坏的 token，这些都不应影响登出成功。

```go
func (h *AuthHandler) Register(r gin.IRouter, guard gin.HandlerFunc) {
	r.POST("/auth/login", h.Login)
	r.POST("/auth/refresh", h.Refresh)
	r.POST("/auth/logout", h.Logout)

	api := r.Group("/api", guard) // 这一组全部过鉴权中间件
	api.GET("/me", h.Me)
}
```

要点：

- **装配全部在 `main`**：config → redis → store → handler → router。依赖是显式传参的，`store` 不放在全局变量里，测试时可以换成假实现。
- **`SetTrustedProxies(nil)`**：关掉 Gin 对 `X-Forwarded-For` 的信任。本机直连场景下不关，客户端可以伪造 `X-Forwarded-For` 绕过任何基于 `ClientIP()` 的限流。前置 nginx 时应改成真实代理网段，而不是留空。
- **`gin.New()` + 显式 `Recovery()`**：不用 `gin.Default()`，避免把调试日志格式固定下来；生产应接自己的结构化日志。
- **优雅退出**：`signal.NotifyContext` 捕获 SIGINT / SIGTERM，`srv.Shutdown` 给在途请求 10 秒收尾。鉴权服务滚动发布时，直接 kill 会切断正在进行的刷新请求。
- **`ReadHeaderTimeout`**：慢速 header 攻击（Slowloris）防护，Go 的 `http.Server` 默认不设这个超时。
- **`/healthz` 顺带 `Ping` Redis**：鉴权强依赖 Redis，健康检查必须覆盖它，否则编排系统会把"连不上 Redis"的实例当成健康实例继续导流。
- **`gin.SetMode(gin.ReleaseMode)`** 只在生产打开，开发环境保留 debug 路由表输出，便于确认路由有没有注册上。

## 六、完整流程与时序

1. **登录**：前端 `POST /auth/login` 提交账号密码 → 校验通过后生成 `refreshToken`（随机）和 `familyId`，把 `sha256(refreshToken)` 存进 Redis → 签发 access JWT → 通过 `Set-Cookie` 下发 refresh，body 只返回 `accessToken`。
2. **业务请求**：前端把 `accessToken` 放内存，请求时带 `Authorization: Bearer <token>` → 中间件验签 + 查黑名单 → 放行并把 `userId` 注入 `c.Set`。
3. **access 过期**：业务请求返回 401 `token_expired`，前端捕获后静默调用 `POST /auth/refresh`。
4. **刷新**：浏览器自动带上 refresh cookie → 后端读 active 记录拿到 `fid` → 用 Lua 原子轮换（旧标 used、新写 active、维护 family）→ 新 refresh 写回 cookie，新 access 返回给前端。
5. **登出**：前端 `POST /auth/logout` 带上当前 access → 后端删 Redis 里的 refresh 记录 + 拉黑 access 的 `jti` + 清 cookie。

```text
浏览器                        Gin (:3001)                      Redis
  |  POST /auth/login            |                               |
  |----------------------------->|  SaveRefresh(h1, family)      |
  |                              |------------------------------>|  HSET go:auth:rt:h1 uid fid
  |                              |                               |  SADD go:auth:rt:family:fid h1
  |<-- Set-Cookie: rt=A ---------|                               |
  |<-- { accessToken: AT1 } -----|                               |
  |                              |                               |
  |  GET /api/me                 |                               |
  |  Authorization: Bearer AT1   |                               |
  |----------------------------->|  ParseAccessToken(AT1)        |
  |                              |  EXISTS go:auth:bl:<jti> ---->|  (0)
  |<-- 200 { userId } -----------|                               |
  |                              |                               |
  |  POST /auth/refresh          |                               |
  |  Cookie: rt=A                |                               |
  |----------------------------->|  HMGET go:auth:rt:hA -------->|  (uid, fid)
  |                              |  EVALSHA rotate ------------->|
  |                              |                               |  EXISTS used:hA  -> 0
  |                              |                               |  EXISTS rt:hA    -> 1
  |                              |                               |  SET used:hA / DEL rt:hA
  |                              |                               |  HSET rt:hB / SADD family
  |<-- Set-Cookie: rt=B ---------|                               |
  |<-- { accessToken: AT2 } -----|                               |
  |                              |                               |
  |  POST /auth/logout           |                               |
  |  Cookie: rt=B, Bearer AT2    |                               |
  |----------------------------->|  RevokeOne(hB, fid) --------->|  DEL rt:hB / SREM family hB
  |                              |  BlacklistAccess(AT2.jti) --->|  SET bl:<jti> EX 剩余秒数
  |<-- 200 { ok: true } ---------|  clearRefreshCookie           |
  |                              |                               |
  |  GET /api/me  Bearer AT2     |                               |
  |----------------------------->|  EXISTS bl:<jti>  ----------->|  (1) -> 401 token_revoked
```

## 七、Refresh Token 轮换与复用检测

这是整套方案的安全核心，值得单独展开。

### 正常轮换

```text
login    -> rt_A(active)
refresh  -> rt_A 标记 used + 删 active  -> rt_B(active)
refresh  -> rt_B 标记 used + 删 active  -> rt_C(active)
```

每次刷新都换发全新的 refresh，旧的立刻失效。攻击者即使拿到某个旧 token，可用的时间窗口也只有一个刷新周期。

### 复用检测

```text
攻击者盗用了 rt_B（此时 rt_C 才是 active）：
  refresh(rt_B)
    -> GET rt:used:hB  命中，返回 familyId
    -> revokeFamily(familyId)  删掉 rt_C 等所有关联 token
    -> 401 refresh_reuse_detected
    -> 正常用户手里的 rt_C 也随之失效，被迫重新登录
```

这里的设计取舍很明确：**安全优先于体验**。宁可误杀正常用户一次（让他重登），也不能让被盗的令牌链继续可用。

### 为什么必须保留 `used` 表

如果轮换时直接删掉旧 token 的痕迹，就没法区分下面两种情况：

| 情况 | 现象 | 应处理方式 |
| --- | --- | --- |
| 攻击者重放一个**曾经有效**的 token | `active` 里查不到，但 `used` 里命中 | 判定被盗，**吊销整条链** |
| 正常用户用一个**从未存在/已过期很久**的 token | 两个表里都查不到 | 直接 401，无需联动 |

`used` 表记录的正是"这个 token 曾经真实有效过"。命中它就等于确认发生了重放——这是唯一能区分上述两种情况的信号。

### 为什么这里必须是 Lua（Go 版与 Node 版的关键差异）

Node 版用的是 `redis.multi()`（MULTI/EXEC）：它保证"这几条命令一起执行"，但**读的结果无法影响后面的写**。所以 Node 版必须先 `getUsed` → 再 `getActive` → 再 `rotate`，这三步之间的窗口就是典型的 TOCTOU：

```text
请求 A: getUsed(hB) -> nil
请求 B: getUsed(hB) -> nil          <-- 同一瞬间，两个请求都通过了"未被使用"检查
请求 A: getActive(hB) -> rec
请求 B: getActive(hB) -> rec
请求 A: rotate -> rt_C(active)
请求 B: rotate -> rt_D(active)      <-- 两个都成功，同一 oldHash 换出两套 token
```

Go 版把这些判断全部搬进 Lua 脚本，Redis 单线程串行执行，第二个请求进脚本时会看到 `used:hB` 已存在，直接返回 `2`。**判断和写入之间不存在任何可插入的窗口。**

### 已知边界：并发刷新

即使有了原子脚本，若客户端因网络重试**并发**发了两次同一旧 token 的 `/refresh`，第二个请求会命中 `used` 判定为复用，触发吊销，把刚换出来的新 token 也一起作废。这是当前的保守策略。

若要优化体验，可在 `used` 命中后引入一个短宽限窗口：把 `used:<hash>` 的值从 `fid` 改成 `fid|unixMillis`，10 秒内的复用只返回 `401 refresh_raced, please retry` 而不吊销整条链（客户端重试一次即可，因为 cookie 已经更新为新值）；超过窗口才判定为盗用。代价是安全强度下降。

客户端侧更稳妥的做法是：**保证同一时刻只有一个刷新请求在飞行**（用一个 promise 做单飞/去重）。

## 八、登出实现

登出要做三件事，缺一不可：

| 动作 | 目的 | 代码 |
| --- | --- | --- |
| 删 Redis refresh 记录 | 让刷新令牌立即失效 | `store.RevokeOne(hash, fid)` |
| 拉黑 access `jti` | 让当前 access 立即失效（不必等自然过期） | `store.BlacklistAccess(jti, ttl)` |
| 清浏览器 cookie | 防止下次请求继续带失效 cookie | `h.clearRefreshCookie(c)` |

关键坑：

| 坑 | 说明 |
| --- | --- |
| 只删 Redis 不清 cookie | 浏览器仍带旧 cookie，每次刷新都 401 |
| `clearRefreshCookie` 的属性与 `set` 不一致 | 浏览器不删 cookie，因为 cookie 按 (name, domain, path) 唯一标识 |
| 忘记拉黑 access | 登出后 access 仍能用到自然过期（最长 `ACCESS_TTL`） |
| 黑名单 TTL 写成固定值 | 应取 `time.Until(exp)`，让 key 随 token 自然过期自动回收 |
| 登出接口强依赖 Bearer | access 可能已过期；登出应只依赖 refresh cookie，Bearer 是"可选加速失效" |
| 登出不幂等 | 重复登出、cookie 已清空都应返回 200，不能报错 |

### 当前设备 vs 全部设备

- `RevokeOne(hash, fid)`：只登出当前设备，同账号其他设备的 token 不受影响。
- `RevokeFamily(fid)`：吊销整条链，用于"登出全部设备"或复用检测触发时。

要支持"登出全部设备"，需在登录时记录 `userId -> Set<familyId>` 的反向索引，登出全部时遍历所有 family 调用 `RevokeFamily`。当前实现未包含这层索引。**改密码 / 封号场景同理**：必须主动调 `RevokeFamily`，否则旧 refresh 能一直换出新 access。

## 十、关键校验清单

- [ ] `JWT_SECRET` 独立生成（`openssl rand -base64 48`），长度 ≥ 32 字节，且不与 `SESSION_SECRET` 复用。
- [ ] `.gitignore` 里包含 `.env`，**不要**把真实密钥提交进仓库。
- [ ] `KEY_PREFIX` 与同 Redis 实例上的其他实现区分开（本仓库 Node 版用裸 `rt:`，Go 版用 `go:auth:`）。
- [ ] 校验端显式锁算法白名单（`jwt.WithValidMethods`），防 alg 混淆 / `alg=none`。
- [ ] 校验端强制 `iss` / `aud` / `exp`，并设 `WithLeeway` 容忍时钟偏移。
- [ ] Redis 里只存 token 的 SHA-256，**不存明文**。
- [ ] 轮换的"检查 + 写入"在同一个 Lua 脚本里完成，不拆成多次 Redis 调用。
- [ ] `/auth/refresh` 的判定顺序：先 `active` → 不在再看 `used` 区分重放与无效 → 最后 `rotate`。
- [ ] 检测到复用时吊销整条 family，而不是只拒绝当前请求。
- [ ] `used` 标记保留到 TTL 自然过期，不在轮换时删除。
- [ ] refresh cookie 五件套齐备：`HttpOnly` + `Secure`（生产）+ `SameSite=Strict` + `Path=/auth` + `MaxAge`。
- [ ] `clearRefreshCookie` 的 `Path` / `Domain` / `Secure` / `SameSite` 与 `set` 完全一致。
- [ ] 登录响应不返回 refresh token，只通过 `Set-Cookie` 下发。
- [ ] 登出同时：删 refresh 记录 + 拉黑 access `jti` + 清 cookie，且幂等。
- [ ] access 黑名单 TTL 用 `time.Until(exp)`，不是固定值。
- [ ] Redis 故障时鉴权 fail-closed（503），不放行。
- [ ] `SetTrustedProxies(nil)`（无代理时）或填真实代理网段，避免 `X-Forwarded-For` 伪造。
- [ ] `http.Server` 设 `ReadHeaderTimeout`，并有 SIGTERM 优雅退出。
- [ ] `go vet ./...` 与 `gofmt -l .` 无输出。

## 十一、安全边界与生产注意事项

### 已经覆盖的威胁

| 威胁 | 防护手段 |
| --- | --- |
| XSS 窃取长期凭证 | refresh 在 HttpOnly cookie，JS 读不到；access 在内存，短命 |
| CSRF 利用 cookie 触发刷新/登出 | `SameSite=Strict` + `Path=/auth` |
| refresh token 泄露后长期可用 | 短期轮换 + 复用检测吊销整条链 |
| 并发刷新导致重复签发 | Lua 脚本把"检查 + 写入"做成原子操作 |
| Redis 数据泄露 | 只存 SHA-256 摘要，无法反推也无法直接使用 |
| 登出后 access 仍可用 | `bl:<jti>` 黑名单 + TTL 对齐剩余寿命 |
| JWT 篡改 / 算法混淆 | HMAC-SHA256 + 算法白名单 + iss/aud/exp 强校验 |
| 慢速 header 攻击 | `ReadHeaderTimeout` |

### 仍需注意

1. **密钥轮换**：当前只支持单个 `JWT_SECRET`，换密钥会让所有存量 access 立即失效（refresh 仍在，用户可无感刷新）。要做平滑轮换需支持 `kid` + 多密钥并行验签。
2. **多服务场景改非对称签名**：单服务用 HS256 足够（密钥只在服务端）。一旦有第二个服务需要**自行校验** access token，应改成 Ed25519 / RS256：私钥签发、公钥下发，配合 header 里的 `kid` 轮换，避免把签名密钥复制到每个服务。
3. **CORS 白名单**：Go 版当前没有挂 CORS 中间件，浏览器跨域访问会直接被拦。要放开时必须用明确的域名白名单 + `Access-Control-Allow-Credentials: true`（规范禁止 `Allow-Origin: *` 与 credentials 共存）。
4. **Redis 可用性**：鉴权强依赖 Redis（黑名单 + refresh 校验）。Redis 挂掉时受保护接口会返回 503（fail-closed）。要评估是否需要给黑名单查询加进程内短 TTL 缓存（1~5 秒）+ Redis Pub/Sub 失效通知，把 QPS 摊下来并降低 Redis 抖动的影响。
5. **黑名单的每次请求成本**：每个受保护请求都会多一次 `EXISTS`。三种取舍——(1) 保持现状，语义最正确；(2) 进程内小缓存；(3) 干脆不做黑名单，靠短 TTL 兜底，登出只作废 refresh。规模不大就用 (1)。
6. **限流**：`/auth/login` 按 IP + 用户名双维度限流，`/auth/refresh` 按 token 摘要限流。这两个端点是唯一能被打的入口。
7. **多设备与管理**：当前无 `userId -> familyId` 反向索引，"登出全部设备"和"查看登录设备列表"需要补这层。
8. **审计日志**：复用检测命中（`refresh_reuse_detected`）是高价值安全事件，当前已用 `slog.Warn` 记录 `family` / `user`，建议再带上 IP 与 UA 并接告警。
9. **Redis Cluster**：当前 key 名是扁平前缀，脚本跨 4 个 key。上 Cluster 前必须改成 hash tag 让同族 key 落同一 slot —— `token_store.go` 里已经留了注释版的实现：

   ```go
   func (s *TokenStore) activeKey(h, fid string) string { return s.prefix + "rt:{" + fid + "}:" + h }
   func (s *TokenStore) usedKey(h, fid string) string   { return s.prefix + "rt:used:{" + fid + "}:" + h }
   func (s *TokenStore) familyKey(fid string) string    { return s.prefix + "rt:family:{" + fid + "}" }
   ```

   注意 `usedKey` 加上 `{fid}` 之后，**查复用标记时也必须有 fid**。而当前 `Refresh` 是"`active` 查不到才去查 `used`"，那一刻手上还没有 fid —— 所以 Cluster 版本必须额外加一个单键索引 `rt:idx:<hash> -> fid`（单键读取不受 slot 约束）先拿到 fid，再拼出带 hash tag 的 `used` key。

## 十二、客户端对接要点

1. **access 只存内存**，不要写 localStorage / sessionStorage。
2. **跨域请求必须带凭证**：`fetch(url, { credentials: "include" })` 或 axios `withCredentials: true`。只在 `/auth/*` 请求上需要，但因为 cookie 的 `Path` 限制，带上也不会外泄。
3. **401 自动刷新要单飞去重**：多个请求同时 401 时，只发一次 `/auth/refresh`，其余等待同一个 promise 结果，避免并发刷新触发复用检测把自己踢下线。
4. **区分 401 的两种语义**：`token_expired` → 静默刷新后重试原请求；`token_revoked` / `invalid_token` / `refresh_reuse_detected` → 清空内存 access 并跳登录页，不要重试。
5. **刷新失败即跳登录**：收到 `invalid_refresh_token` / `refresh_reuse_detected` 时不要重试。
6. **页面刷新后的静默续期**：access 在内存里，刷新页面就没了。应用启动时先调一次 `POST /auth/refresh` 试恢复会话，失败再进登录态。
7. **不要手动读 refresh cookie**：它是 HttpOnly，本来就读不到；也不要在前端代码里试图设置它。
8. **登出要等服务端响应**：`/auth/logout` 负责吊销服务端状态，不能只在前端清内存（否则服务端 refresh 仍然有效）。记得带上当前 access，否则 access 不会立即进黑名单。
9. **`refresh_reuse_detected` 是安全信号**：若用户频繁遇到，说明有其他端在复用同一个旧 token，或客户端并发刷新有 bug，需排查而不是简单忽略。

## 十三、与 Node 版实现的对照

同一仓库的 `nodejs/express/jsonwebtoken + Redis` 是这套方案的 Node 版，两边**语义完全一致**，差异集中在语言与并发控制上：

| 维度 | Node 版（Express） | Go 版（Gin） |
| --- | --- | --- |
| 端口 | 3000 | 3001 |
| Redis 前缀 | 裸 `rt:` / `bl:` | `go:auth:rt:` / `go:auth:bl:` |
| 模块名 | `package.json` | `module jwt-redis` |
| active 记录 | string（JSON） | hash（`uid` + `fid`） |
| 原子性手段 | `multi()` 事务 | **Lua 脚本**（判断 + 写入不可分割） |
| 复用检测时机 | `/refresh` 里先 `getUsed` 再 `getActive`（存在 TOCTOU 窗口） | 全部在脚本内完成（无窗口） |
| Cookie 解析 | `cookie-parser` | 标准库 `http.SetCookie` / `c.Cookie` |
| JWT 库 | `jsonwebtoken` v9 | `golang-jwt/jwt/v5` |
| 时间声明校验 | 默认只验 `exp` | 显式 `iss` / `aud` / `exp` + `WithLeeway` |
| 算法白名单 | 未显式限制（v9 默认推导） | `WithValidMethods(["HS256"])` 强制 |
| 过期 access 的 jti | `verify` 抛错后 `catch` 忽略 | `WithoutClaimsValidation` 单独解析 |
| Redis 故障时 | try/catch 返回 401 | **fail-closed 503** |
| 复用错误码 | `reuse_detected` | `refresh_reuse_detected` |
| access 过期错误码 | `invalid_or_expired_token`（合并） | `token_expired` / `invalid_token`（分开） |
| 配置加载 | dotenv 多路径（子项目 `.env` + 根 `.env`） | `godotenv.Load()` 单文件（多路径加载函数已写但未接） |
| 启动方式 | `app.listen` | `http.Server` + 信号优雅退出 |
| 健康检查 | 无独立端点 | `GET /healthz`（含 Redis Ping） |
| 测试脚本 | `test/auth.http` | `test/auth.http`（多覆盖复用检测与黑名单用例） |

> 两套实现可以同时跑、共用同一个 Redis 实例，靠 `KEY_PREFIX` 隔离。做对照实验时注意别把端口和前缀搞混。

## 十四、待改进项（代码走查结论）

以下都是走查实现时发现的问题，按优先级排列。**没有安全漏洞**，但有几项会影响可维护性或埋坑。

| # | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| 1 | `.gitignore`（空文件） | `.env` 里是真实 `JWT_SECRET`，当前没有忽略规则，一旦 `git add .` 就会把密钥提交上去 | 立即写入 `.env` 等忽略项 |
| 2 | `go.mod` | 所有依赖都被标了 `// indirect`，包括 gin / jwt / redis 这些直接依赖 | 跑一次 `go mod tidy` 修正 |
| 3 | `middleware/auth.go` | Redis 报错分支 `AbortWithStatusJSON(503, ...)` 后**漏了 `return`**，会继续走到 `ctx.Next()`。因为 gin 的 `Abort()` 会把 index 推到 `abortIndex`，`Next()` 实际是空操作，**行为正确**，但不够显式 | 补上 `return` |
| 4 | `services/token_store.go` | `BlacklistAccess` 的守卫是 `if ttl < 0`；若传入 `ttl == 0`，`redis.Set` 的语义是**永不过期**，会留下永久黑名单键（当前调用点已用 `ttl > 0` 挡住，但守卫本身应该更严） | 改成 `if ttl <= 0` |
| 5 | `services/token_store.go` | `Rotate` 上的注释是复制粘贴残留（写成"返回该 token 曾经所属的 family"，实际是执行轮换） | 修正注释 |
| 6 | `config/config.go` | `loadEnvFiles()` / `findUpAll()` 已实现但从未被调用（`Load()` 用的是单文件 `godotenv.Load()`）。Node 版靠多路径加载复用根目录 `.env` 里的 `REDIS_*`，Go 版目前必须把 Redis 配置复制到子项目 `.env` | 要么接上，要么删掉 |
| 7 | `utils/token.go` vs `routes/auth.go` | 同一项目混用两套 UUID：标准库 `uuid`（Go 1.27 新增）与 `github.com/google/uuid` | 统一成一种；若要兼容更老的 Go 工具链，统一用 `google/uuid` |
| 8 | `go.mod` | `go 1.27.0` + 标准库 `uuid`，意味着这个子项目无法用 Go 1.26 及更早的工具链构建 | 在 Dockerfile / CI 里固定 1.27+ 镜像 |

## 附：一句话总结

**JWT 管"每次请求都要验的那部分"——走内存和签名；Redis 管"必须能撤销的那部分"——走摘要和 TTL；两者之间用"短 access + 长 refresh + 每次轮换"缝合，而轮换的判断与写入用 Lua 做成原子。**
